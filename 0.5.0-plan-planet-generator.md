# 0.5 — Lazy planet systems: selection, generation, schematic view, delta-v, routes

Source brief: `archive/0.5-draft-planet-generator.txt`. The engine today ends at the
star: 300k `StarPacked` records, three render paths, three movement engines, one global
star time, and a click picker that can only hit the ~60 named landmarks. 0.5 goes one
level down — a star can be *opened*, and inside it there are planets, belts, a delta-v
map and routes between them.

Six releases, each shippable alone:

| Release | Theme | One line |
|---|---|---|
| 0.5.0 | Star selection | Pick **any** drawn star (not just landmarks), keep a primary plus a multi-select set, add "select around", fly to the selection. |
| 0.5.1 | Planet systems | The lazy deterministic generator: star → planets, belts, habitable zone, temperatures. Hash-keyed, never resident, derived on demand. |
| 0.5.2 | Search | Filter stars by type and planets by type/temperature; scope = the selection, or the whole galaxy when nothing is selected. |
| 0.5.3 | System view | The close-system schematic: log-polar orbits, colour-coded planet icons, belts, habitable band, click-to-select, an editor readout. |
| 0.5.4 | Delta-v map | Node graph and table: surface / low orbit / GEO / L5 / belt, with travel time at a chosen energy budget. |
| 0.5.5 | Routes | Ship classes, two-way trade routes with synodic windows, one-way autopilot, the ship icon moving on the schematic. |

Dependency chain: 0.5.1 needs 0.5.0's star identity, 0.5.2 needs 0.5.1's summary tier,
0.5.3 needs 0.5.1, 0.5.4 needs 0.5.1 + 0.5.3, 0.5.5 needs 0.5.4. 0.5.0 is useful on its
own and changes no model contract.

Ground rules inherited unchanged: the density field is the source of truth, stable hash
with no PRNG state, no allocations in the frame loop, `file://` classic scripts, one API
object per file exposed to both environments, WGSL only in `src/render/shaders.js`,
plans before code. §1 states the two rules this series *adds*.

---

## 1. The two new ground rules

### 1.1 Planets are CPU-only

No WGSL, no `StarPacked` growth, no new GPU buffers, no new render path. Planets, belts,
the delta-v graph and ships are computed in JS and drawn on a 2D canvas overlay above the
WebGPU canvas — the same technique `src/render/label-layer.js` already uses for names,
constellation lines and the selection ring.

Why, explicitly:

* **The count does not justify a pipeline.** A system is ≤ 12 planets + 2 belts + 1 ship.
  A GPU path for that is a storage buffer, a bind group, a compute or vertex shader, a WGSL
  mirror to keep in parity, and a `wgsl-validate` pin — for 400 bytes of data that the CPU
  can recompute in 20 µs. The star field needs the GPU because it is 300k records; a
  planetary system needs a canvas because it is 15 circles.
* **The 16-byte record is a contract, not a scratchpad.** `archive/0.4.0-plan-star-move.md`
  §1.3 exists because movement had to fit in bits already spare. Planets do not fit and
  should not be squeezed in: a planet is not a star (different size scale, different
  render primitive, different lifetime — it exists only while its system is open).
* **The brief asks for a schematic, not a simulation.** "planets as icon with color coded
  types", "no need real sizes of planets, but easy to view and select". A 2D log-polar
  schematic is the honest rendering of that sentence, and it is readable at a glance where
  a true-scale 3D system (planets 1e-5 of the frame) is invisible.

Acceptance consequence: `wgsl-validate`, `wgsl-exec`, `renderer-test` and the star shader
are **not touched** by this series. If a task seems to need a WGSL change, the task is
wrong. The only renderer change is read-only accessors (§2.2) plus one parallel identity
array.

### 1.2 Generation is lazy and never resident

There is no galaxy-wide planet table, no per-cell planet payload, no cache that grows with
play. A system is derived when (a) a star becomes the primary selection, (b) a search
filter asks for a summary, or (c) the system view opens. Deriving it twice gives
byte-identical results, because it is a pure function of a key — the same rule the star
field lives by (`AGENTS.md`, "Stable hash, no PRNG state").

The one thing that *is* kept is small and bounded: the selection set (§3, 256 snapshots,
18 KB) and the search result buffer (§5, 512 entries, 41 KB). Both are allocated once at
boot and mutated in place.

Rejected alternative: baking planet systems into the catalog bundle
(`src/data/tiles/catalog.js`, 168 KB today). That would make the Milky Way preset's 3,829
catalog stars ship with authored systems — 3,829 × the 1.4 KB `SystemRecord` of §4.9 is
5.4 MB, 7.2 MB once base64-encoded, i.e. forty times the current bundle for data a hash
produces for free in 20 µs. It would also fork the pipeline into "catalog planets" and
"procedural planets", exactly the two-list drift `star-record.js` was written to end.

## 2. Star identity — the key everything hangs off

### 2.1 The problem: streaming slots are not identities

The star buffer is one flat staging `ArrayBuffer` in five blocks
(`src/render/star-sprites.js`, `prepare()`):

```
[ procedural field ][ landmarks ][ composite objects ][ local gap-fill ][ catalog ]
```

The first three are written once per galaxy; the last two are rewritten whenever the
camera moves and the residency set changes (`uploadDynamic()`). The renderer already says
so in a comment: *"Streaming slots are not stable star identities"* — which is why the
simple engine re-seeds their azimuths on every rebuild.

So a selection that stored `bufferIndex` would silently become a different star as soon as
the viewer flies. Two consequences drive the design:

1. **Every drawn star gets a stable `u32` key**, written next to its record.
2. **A selection stores a snapshot, not an index** (§3.2).

### 2.2 The identity array

`star-sprites.js` gains one parallel array, allocated with the staging buffer and filled
wherever a block is written:

```
identity = new Uint32Array(totalRecords)   // 4 B per record, same slot order as staging
```

| block | key | source |
|---|---|---|
| procedural field | `fieldStarSeed(model.seed, i)` | already computed in `writeProceduralRecords()` — `StarTypesLib.fieldStarSeed`, `seed*31 + i + 1` |
| landmarks | `hash4(DOMAIN_LANDMARK, i, 0, 0)` | index into `landmarks.ENTRIES` |
| object members | `objectMemberSeed(obj.seed, i)` | already computed in `objects.writeObjectMembers()` |
| local gap-fill | `slotSeed` | already computed in `writeLocalProceduralStars()` — `imul(localSeed,·) ^ imul(cell.id,·) ^ imul(i+1,·)` |
| catalog | `hash4(DOMAIN_CATALOG, cell.id, slotInCell, 0)` | filled in the `manager.writeInto()` loop, which already walks cells |

`DOMAIN_LANDMARK = 0x1A4D7E11`, `DOMAIN_CATALOG = 0x2B5E8F32` — arbitrary non-zero
constants, chosen once, never changed (a domain change re-rolls every system in the
galaxy). Keys are only required to be *stable* and *collision-free in practice*; a 32-bit
PCG output over ~300k keys collides with probability ~1e-5 per galaxy, and a collision
costs two stars the same planetary system — invisible, not a correctness bug. The
generator's own seed adds a second hash (§4.2), which makes even a key collision produce
different systems in different galaxies.

Renderer API additions (read-only, built at `prepare()`/`regenerate()`, never per frame):

```js
renderer.starBlocks()   // { identity, view, blocks: [{kind, offset, count}, …], total }
renderer.fieldBuffers() // the sampling buffers: x, y, z, R, distToArm, component, count
```

`blocks` is a fixed five-entry array allocated once; the counts are mutated in place by
`prepare`/`uploadDynamic`, so no object is created per frame and none per pick.

### 2.3 The system seed and the channel map

`planets.js` derives everything from one domain-separated seed:

```js
systemSeed = hash4(key, model.seed, DOMAIN_PLANETS, blockKind)   // DOMAIN_PLANETS = 0x51A7E75
```

`model.seed` is in the key so a new galaxy re-rolls its planets; `blockKind` keeps a
landmark and a field star with equal keys apart. Inside a system, every draw is
`hash01At(systemSeed, channel)` with this fixed channel map — the equivalent of the star
pipeline's `seed*31 + n` channels, written down so two features cannot silently share a
draw:

| channels | quantity |
|---|---|
| 0 | system dynamical temperature (`eScale`) |
| 1 | spare |
| 2 + n | count chain slot n, n = 0 … MAX_PLANETS−1 (channels 2–13; 14–31 spare) |
| 32 + 8·p | planet p: bulk class |
| 33 + 8·p | planet p: semi-major axis |
| 34 + 8·p | planet p: mass within the bulk range |
| 35 + 8·p | planet p: eccentricity |
| 36 + 8·p | planet p: inclination |
| 37 + 8·p | planet p: argument of periapsis |
| 38 + 8·p | planet p: phase at system time 0 |
| 39 + 8·p | planet p: rotation period |
| 128 + p | planet p: moon count, p = 0 … 11 (the 8-wide planet slot ends at 39+8·p, so twelve planets fill 32 … 127 and leave 128 … 199 free — where moon counts live, one channel each, without touching the next planet's slot) |
| 200 | inner belt: presence |
| 201–204 | inner belt: radius factor, width, mass, stipple seed |
| 210 | outer belt: presence |
| 211–214 | outer belt: radius factor, width, mass, stipple seed |
| 300 + s | belt stipple angle/radius draw s, s = 0 … 2·STIPPLE_N−1, on the belt's **own** stipple seed (the raw word of channel 204 / 214) |

`p` is the planet's index **in the record**, i.e. outward order: §4.5 draws the axes and
sorts them before anything else is drawn, so every later per-planet channel is already
keyed by the position the readout and the delta-v map will name it by. `planet-gen-test.js`
claims the whole map into one set and fails on the first duplicate, because a collision one
planet in is invisible until the systems disagree.

The reserved space, so a 0.5.x extension does not renumber anything that shipped: channel 1,
channels 14–31 (the count chain's spare slots, `MAX_PLANETS + 12` of them), and 128–199 for
exactly what the moon counts already used — one channel per possible planet.

Channels 0–7 of the *star* seed (mass, age ×2, evolution ×2, component) are never reused:
`systemSeed` is a fresh 32-bit value, so its channel space is independent by construction.

### 2.4 Stellar inputs per block

The generator needs `(mass M☉, luminosity L☉, Teff K, R★, age Gyr, Z, state, spectral
class)`. How each block supplies them — one helper, `planets.stellarInputs(ref, out)`:

| block | path | exactness |
|---|---|---|
| procedural field | `StarTypesLib.deriveStar(model, key, component, R, distToArm, out, z)` with `component/R/distToArm/z` from `renderer.fieldBuffers()` | **exact** — the same call, the same arguments, the same channels the renderer used to write the record |
| local gap-fill | `deriveStar(model, imul(slotSeed,31)+5, …)` — the renderer's own `deriveSeed`, with `component/R/distToArm` re-derived from the record position through `density.rhoDecomposed` | exact to the f32 position the record carries |
| object members | `StarTypesLib.deriveStarWithAge(model, memberSeed, component, R, distToArm, ageGyr, out)` with the object's coeval age | exact |
| landmarks | `massFromClassAndMag(class, absMag)` from the entry's `colorIndex` + `absMag`; age from the model population | **derived**, §2.5 |
| catalog | same helper, from the record's `colorIndex` + `absMag` (16-byte record, nothing else survives the encoder) | **derived**, §2.5 |

The parity rule the repo already applies to labels and picking applies here: *the star the
viewer selects must be the star the generator describes*. For the three procedural blocks
that is bit-exact by construction. For landmarks and catalog stars the record genuinely
does not carry a mass, so it is inverted from the two numbers it does carry.

### 2.5 `massFromClassAndMag` — inverting what the record kept

```
L/L☉  = 10^((4.83 − M_V)/2.5)                      // StarTypesLib.absoluteMagnitude, inverted
M/M☉  = luminosityFromMass⁻¹(L), searched inside the class's mass bracket
```

`luminosityFromMass` is piecewise power-law (α = 2.3 / 4.0 / 3.5 / 2.8 at
M < 0.7 / < 2 / < 20 / ≥ 20), so the inverse is closed form per branch; the class
bracket picks the branch and clamps:

| class | bracket (M☉) |
|---|---|
| O | 16 – 100 |
| B | 2.5 – 16 |
| A | 1.6 – 2.5 |
| F | 1.05 – 1.6 |
| G | 0.85 – 1.05 |
| K | 0.55 – 0.85 |
| M | 0.08 – 0.55 |
| WD | 0.5 – 1.4 — remnant mass; L is ignored, use the cooling-track mass |
| RG / RGe | 0.8 – 3.0 — initial mass; L is the giant's, not the MS one |

Pins (`experiments/planet-gen-test.js`): the Sun (G, M_V 4.83) → 1.000 ± 0.02 M☉,
L 1.00 ± 0.02 L☉; Sirius A (A, M_V 1.43) → 2.0 ± 0.2 (2.19 measured); a K landmark
(61 Cyg-class, M_V 7.5) → 0.70 ± 0.06. Giants and white dwarfs are **not** required to
invert to their birth mass — for them the bracket's midpoint is the contract, and the
generator treats them by `state`, not by mass (§4.4 handles engulfment and remnant disks).

The rule that produces those three numbers, so the test can pin it and a reader can
re-derive it: L comes from M_V, the class bracket picks the power-law branch its *lower*
bound sits in, and the closed-form inverse is clamped to the bracket. A class whose
bracket cannot reach the inverted luminosity at all — a late K star dimmer than 0.55 M☉
allows — is answered with the bracket's **midpoint**, not the clamp: the law has nothing
to say about it, the class does. That is the 61 Cyg case, and it is why the K pin is a
number rather than a wall.

Stellar radius, needed for the innermost orbit and for equilibrium temperature:

```
R★/R☉ = sqrt(L/L☉) · (5772/Teff)²
```

Sun → 1.000 by construction (the derived path's Teff comes from `teffFromMass`, 5800 K at
1.0 M☉, so the measured radius is 0.990 R☉ — within 1 %, which is the pin's tolerance);
a 100 L☉ giant at 4000 K → 20.8 R☉ (real red-giant radii are 5–50 R☉, so this reads
correctly without a second table). Note that the derived path's giant radius is smaller
than a giant track would give, because the mass is a bracket midpoint rather than the
luminosity-consistent radius — the same limitation §2.5's mass inversion accepts.

### 2.6 Dispatch parity for the picker

`selection.pick()` today projects landmark positions through
`OrbitLib.engineLandmarkPosition` — the shared mask dispatch — so a click lands where the
GPU drew. 0.5.0 extends picking to every block, which needs the same dispatch for a
*record* rather than for a landmark:

```js
OrbitLib.engineRecordPosition(out, x, y, z, packed, time, model)
```

reading `family = familyFromFlags(packed)` and `{phase, amplitude} = readOrbit(packed)`
from the record itself (both helpers already exist and are exported), then running the
identical mask ladder `engineLandmarkPosition` runs.

The `simple` bit is the honest gap: its CPU mirror
(`simpleLandmarkPosition`) covers landmarks only, because field-star θ lives in a GPU
compute buffer the CPU never reads back (`AGENTS.md`: indirect draw, no readback). So:

* masks **without** the simple bit (1, 4, 5) → picking is exact, all blocks.
* masks **with** the simple bit (2, 3, 6, 7) → the picker uses the classic/identity
  baseline for the two streaming blocks and reports it: the readout line ends with
  `(position approximated: simple engine keeps star θ on the GPU)`. Landmarks stay exact.

This is `movement-parity-plan.md`'s open item, not a new one; when that plan lands a
field-star θ mirror, the approximation disappears and the readout suffix is deleted. Do
not build a second mirror here.

## 3. 0.5.0 — Star selection

### 3.1 Picking any drawn star

`src/core/selection.js` keeps its job (project, find the nearest within
`PICK_RADIUS_PX = 20`) and gains a second entry point that walks the whole buffer:

```js
pickAny(x, y, width, height, out)  // out: { key, blockKind, index, x, y, z, packed, dist2 }
```

* Walk the five blocks in order; skip records without `FLAG_VISIBLE`; project with
  `coords.projectToScreen` (which already culls `clip.w ≤ 0`).
* Nearest in screen distance wins. Tie-break inside `PICK_TIE_PX = 3`: brighter
  `absMag` wins, so a click on a pair does not select the faint star behind the bright one.
* Cost is one pass over resident records at click time — never per frame. At 300k
  procedural stars that is ~300k projections ≈ 6 Mflop. **Budget: < 16 ms** on a laptop
  core, measured in `experiments/star-select-test.js`. If the measurement misses, the fix
  is a coarse pre-reject (skip records whose world position is more than
  `2·tan(FOV/2)·dist` off the view axis, one dot product) — not a spatial index that has
  to be maintained per frame.
* The existing landmark-only `pick()` stays for the label layer's ring; `main.js` calls
  `pickAny` first and falls back to nothing (a miss is a no-op, as today).

### 3.2 The selection set — snapshots, not indices

New file `src/core/star-set.js`. Capacity 256, allocated once, struct-of-arrays:

```
keys      Uint32Array(256)      // §2.2 key
blockKind Uint8Array(256)       // which block it came from
bufferIdx Uint32Array(256)      // where it was when selected — may go stale (§3.5)
x,y,z     Float64Array(256)     // kpc, f64 like the CPU side of the engine
mass,lum,teff,age,metal Float64Array(256)   // stellar inputs, derived once at select time
colorIndex Uint8Array(256)
absMag    Float32Array(256)
count     // entries in use, nearest-first
primary   // index into the set, or -1
```

A snapshot costs one stellar derivation at select time and then never touches the model
again: no re-derivation when the camera moves, no stale-index arithmetic, and the set
survives a residency rebuild because it holds positions, not slots. `bufferIdx` is used
for one thing — drawing a ring on the selected star in the sky — and is refreshed by key
when the block is rebuilt (§3.5).

Rules:

* **Primary + set, both kept** (the brief: "we keep both 1st selected and multiple
  selected"). The primary drives single-star operations (system view, editor readout,
  fly-to); the set drives bulk ones (search scope, radius select, routes between members).
* A plain click sets the primary **and** the set to that one star. Shift+click toggles
  membership without moving the primary. `N` / `Shift+N` cycle the primary through the set.
* Capacity overflow drops the **farthest from the camera**, matching the cell manager's
  nearest-first budget rule, and reports `+n dropped` in the readout.
* A model change (type / seed / regenerate) clears the set — another galaxy is another set
  of stars, exactly as `regenerateGalaxy()` already drops `selected`. An **age** change
  does not: positions do not move under an age change, so the snapshots stay valid, but
  their `mass/lum/teff/age` fields are stale → the set is re-derived in place from the keys
  (256 derivations, ~50 µs), not dropped.

### 3.3 Select around

Menu button **Select around** plus a log-scale radius slider. The radius is **world-space,
in light-years**, not screen-space: a screen radius would collect stars at wildly
different distances, and the operations the set exists for (a trade route, a search over a
neighbourhood) are physical.

```
slider  0.1 … 100 000 ly, log10, default 50 ly     preset field `selrad`
```

Scan: one pass over the resident records, `d² = (x−px)² + (y−py)² + (z−pz)²` against the
primary's snapshot position, collect inside the radius, sort by distance ascending
(insertion sort into the preallocated key array — n ≤ 256), truncate at capacity. At 300k
records that is ~300k distance checks, **budget < 5 ms**, measured in the same test.
The result *includes* the primary at index 0, so "select around" on a lone star always
leaves a non-empty set.

Readout: `selected 214 stars within 50 ly of Sirius A (primary Sirius A)`.

### 3.4 Fly to the selection

`camera.js` gains `flyToStar(x, y, z, name, standOffKpc)`:

* `assignObjectTarget(x, y, z, name)` → `setMode(MODE_ORBIT_OBJECT)` → `snapToOrbit()`,
  with `orbitDistance = clamp(standOffKpc, ORBIT_DISTANCE_MIN, ORBIT_DISTANCE_MAX)`.
* `standOffKpc = clamp(0.0006 · sqrt(L/L☉), ORBIT_DISTANCE_MIN, 0.01)` — 2 ly for the Sun
  clamps to the 0.1 pc floor, a 10 000 L☉ supergiant stands off at ~6 pc so the disc fits.
  The floor is the existing `ORBIT_DISTANCE_MIN`; do not lower it in this series (the
  near-plane and the sprite size ramp are tuned against it).
* Key `F` and a menu button; from the system view `F` re-centres on the primary.

This is the brief's "in fly mode some function to fly to selected star". It is a camera
move, not a mode change: after `F` the viewer is in `orbit object` and can still `C` back
to fly.

### 3.5 Sky highlight for set members

`label-layer.js` already draws one ring on `selected`. It gains
`setSelectedKeys(keys, count)` and draws a smaller, dimmer ring (`SET_RING_PX = 4`,
`rgba(255,215,94,0.45)`) on every set member it can resolve. Resolution is by
`renderer.starBlocks().identity` — a single pass building a key→slot map **only when the
set changes or the dynamic blocks are rebuilt** (an `Int32Array` keyed by
`key & (MAP_SIZE−1)`, `MAP_SIZE = 1024`, open addressing; allocated once). Not per frame:
the layer draws from the resolved slot array it already has.

### 3.6 Readout

`#overlay` gains two lines, formatted like the existing `selectedLine`:

```
selected  Sirius A  (A1V, 1.98 M☉, 24.3 L☉, 24 600 ly)     [V system view]
set       214 stars within 50 ly · N next · X clear · F fly to
```

For an unnamed star the designation is §4.10's `S<key36>` form.

### 3.7 What 0.5.0 must pin

* `pickAny` hits the star the GPU drew: for masks 1/4/5 the picked record's projected
  position equals the dispatched position within 0.5 px (the existing landmark parity
  test, generalised to all blocks).
* Picking is a no-op on a miss and never throws on an empty residency set.
* Shift+click toggle, `N` cycling, capacity overflow dropping the farthest, clear on
  regenerate, re-derive on age change.
* Radius select returns exactly the records inside the radius (checked against an
  independent brute-force list) in ascending distance order.
* Snapshot stellar inputs equal a fresh `deriveStar` for the same key — the anti-drift pin.

## 4. 0.5.1 — The planet system generator

New file `src/math/planets.js`, loaded after `star-types.js` (it reads
`luminosityFromMass`, `teffFromMass`, `MASS_TEFF_TABLE`, `absoluteMagnitude`) and after

### 4.1 Constants

```
AU_M          = 1.495978707e11       M_SUN_KG = 1.98892e30
G_SI          = 6.674e-11            M_EARTH_KG = 5.9722e24
R_EARTH_M     = 6.371e6              R_SUN_M  = 6.957e8
TEFF_SUN      = 5772                 RHO_EARTH = 5514      // kg/m³

RUNAWAY_DT    = 500                  // K; the runaway-greenhouse branch (§4.2), Venus-calibrated

AIRLESS_M     = 0.02                 // M⊕; below this no atmosphere is retained at all

```

### 4.2 Planet display types (the icon table)

Ten display types, one row each — colour is the icon fill in the system view, and the
column the search filter names. Colours are sRGB bytes like `star-record.js`'s
`CLASS_COLORS`, chosen to be separable on a dark background and deliberately *not* the
star palette's blues-for-hot convention (a blue planet and a blue star must not read the
same).

| id | name | bulk | icon colour | albedo | atmosphere | ΔT base (K) |
|---|---|---|---|---|---|---|
| 0 | LAVA | rock | `255, 90, 42` | 0.10 | none | 0 |
| 1 | BARREN | rock | `154, 143, 130` | 0.12 | none | 0 |
| 2 | DESERT | rock | `217, 164, 91` | 0.28 | thin | 8 |
| 3 | TERRAN | rock | `79, 157, 224` | 0.30 | breathable | 33 |
| 4 | ICE | ice | `207, 232, 245` | 0.65 | thin | 8 |
| 5 | SUPER_EARTH | super | `164, 209, 106` | 0.25 | thick | 40 |
| 6 | MINI_NEPTUNE | mini | `127, 212, 208` | 0.45 | H/He | 60 |
| 7 | GAS_GIANT | gas | `224, 176, 112` | 0.50 | H/He | 30 |
| 8 | ICE_GIANT | icegiant | `111, 159, 224` | 0.55 | H/He | 25 |
| 9 | DWARF | dwarf | `122, 122, 122` | 0.10 | none | 0 |

The `atmosphere` column is the one the delta-v module reads for drag, aerocapture and
landing credit (§7.2) — one table, three consumers, no second list to drift.

ΔT is added to the equilibrium temperature to give the *surface* temperature the search
filters on. Two rules modify the base value, both physical rather than fitted:

* **The carbonate-silicate thermostat** (Walker, Hays & Kasting 1981) applies to TERRAN and
  SUPER_EARTH: a colder world outgasses more CO₂, so the greenhouse term grows as
  insolation falls. `ΔT = min(65, 33 + 55·clamp(1 − S, 0, 1))`. This is what makes the
  whole habitable band habitable instead of only its inner edge: at S = 1 it is 33 K
  (Earth, 288 K), at S = 0.58 it is 56 K (278 K), at S = 0.35 — the outer edge — it
  saturates at 65 K (261 K, since Teq has fallen to 196 K there: 196 + 65 = 261).
* **The runaway greenhouse** is a bifurcation, not a gradient: a rocky/icy/super world of
  `M ≥ ATM_RETAIN_M` above the HZ inner edge boils its oceans and never comes back.
  `band = 1 and M ≥ 0.3 → ΔT = RUNAWAY_DT = 500`, flag `runaway`, display DESERT, and —
  because a runaway world is cloud-shrouded — **albedo 0.70** rather than the display
  type's. Below 0.3 M⊕ there are no volatiles left to run away with, so a Mercury-like
  world at S = 6.7 keeps `ΔT = 0` and stays at its equilibrium temperature, which is the
  correct answer.

Pins around a Sun-like star (R★ 1 R☉, Teff 5772 K), all six from these constants and the
§4.6 refinement table — the albedo column is what the table assigns, not what was tuned
(`experiments/planet-gen-test.js`):

| body | a (AU) | M (M⊕) | type | A | Teq | ΔT | Tsurf | published |
|---|---|---|---|---|---|---|---|---|
| Mercury | 0.387 | 0.055 | BARREN | 0.12 | 433 | 0 | **433** | 440 K (day) |
| Venus | 0.723 | 0.815 | DESERT + runaway | 0.70 | 242 | 500 | **742** | 737 K |
| Earth | 1.000 | 1.000 | TERRAN | 0.30 | 255 | 33 | **288** | 288 K |
| Mars | 1.524 | 0.107 | DESERT | 0.28 | 208 | 8 | **216** | 210 K (mean) |
| Moon | 1.000 | 0.012 | BARREN | 0.12 | 270 | 0 | **270** | 250 K (mean) |
| Ceres | 2.766 | 0.00016 | DWARF | 0.10 | 163 | 0 | **163** | 168 K |

### 4.3 Bulk classes: mass range, mass–radius law, rotation

Seven bulks. `R/R⊕ = Rref·(M/Mref)^p` — the law is per bulk because a rocky world and a
gas giant of equal mass differ by a factor of 10 in radius, and one global law is what
makes generated systems read as wrong.

| bulk | M range (M⊕) | Mref | Rref (R⊕) | p | rot range (h) | ρ check |
|---|---|---|---|---|---|---|
| rock | 0.05 – 2.0 | 1 | 1.00 | 0.28 | 8 – 60 | 1 M⊕ → 5514 kg/m³ ✓ |
| ice | 0.05 – 2.5 | 1 | 1.10 | 0.28 | 8 – 60 | 1 M⊕ → 4170 ✓ (icy, less dense) |
| super | 2 – 10 | 5 | 1.60 | 0.27 | 8 – 40 | 5 M⊕ → 1.6 R⊕ ✓ (Kepler-11f class) |
| mini | 5 – 20 | 10 | 2.80 | 0.50 | 8 – 20 | 10 M⊕ → 2.8 R⊕, ρ 2460 ✓ |
| gas | 50 – 3000 | 318 | 11.20 | 0.05 | 8 – 18 | 318 M⊕ → 11.2 R⊕, ρ 1250 ✓ (Jupiter 1330) |
| icegiant | 10 – 60 | 17 | 4.00 | 0.35 | 10 – 20 | 17 M⊕ → 4.0 R⊕, ρ 1600 ✓ (Neptune 1640) |
| dwarf | 0.0005 – 0.05 | 0.01 | 0.20 | 0.30 | 4 – 30 | Ceres-like |

Radius saturates for gas giants by design (`p = 0.05`): a 3000 M⊕ planet is 1.24 R_J,
which is what real cold giants do above ~1 M_J.

Mass inside a bulk's range is drawn **log-uniformly** (`M = M_min·(M_max/M_min)^u`): the
ranges span decades — the dwarf bulk alone spans 100 — so a linear draw would spend every
sample in the top decade and never produce a Ceres. Density comes from the mass and the
radius, `ρ = M/(4/3·π·R³)` with `M_EARTH_KG` and `R_EARTH_M`; the check column is what the
test pins (1 M⊕ → 5514, 318 M⊕ → 1250 for Jupiter's 1330, 5 M⊕ in 1.60 R⊕ → 6730, and the
same law putting a 1.13 M⊕ super-earth at 1.07 R⊕, 3 % off α Cen Bb's observed 1.04).

### 4.4 Occurrence: how many planets, of what

Mean count `μ` by stellar class, from the Kepler/RV census shape (M dwarfs are the most
productive per star, O/B the least):

| class | O | B | A | F | G | K | M | WD | RG | RGe |
|---|---|---|---|---|---|---|---|---|---|---|
| μ | 0.02 | 0.10 | 0.35 | 0.90 | 1.20 | 1.30 | 1.60 | 0.15 | 0.40 | 0.30 |

Two modifiers:

* **Metallicity, on giants only.** `f_Z = clamp((Z/0.020)², 0.05, 4)` scales the `gas`,
  `icegiant` and `mini` weights. This is Fischer & Valenti's `P(giant) ∝ 10^(2[Fe/H])` with
  `[Fe/H] = log10(Z/0.020)`, and it reads straight off the model the engine already has:
  `metallicityFor(component)` gives 0.020 thin disc, 0.008 thick, 0.035 bulge, 0.001 halo —
  so bulge stars are giant-rich and halo stars giant-poor with no new authoring.
* **State, on architecture.** A `giant` star has already engulfed its inner system: `a_0`
  is raised to the star's current radius × 1.5 and the `rock`/`ice`/`super` weights are
  scaled by 0.25 (only wide survivors). The ×1.5 factor is subsumed by `STAR_CLEARANCE = 6`
  (a 20 R☉ giant gets its innermost orbit at 0.56 AU, which is 120 R★), so the code writes
  `a_0 = max(0.012, STAR_CLEARANCE·R★_AU, 1.5·R★_AU)` and the giant rule's real content is
  the weight scaling. A `wd` keeps a compact debris ring: `a_out` is cut to
  `min(DISK_OUT_AU·sqrt(M★), 1 AU)`, the bulk table is restricted to `rock` and `dwarf`,
  and the inner belt runs at 80% presence (the real polluted-WD picture).

**Count draw** — a geometric chain, no PRNG state, allocation-free:

```
n = 0
while (n < MAX_PLANETS && hash01At(systemSeed, 2 + n) < μ/(μ + n + 1)) n++
```

Its mean is analytic: `E[n] = Σ_{k≥1} Π_{j≤k} μ/(μ+j)`, and `P(n ≥ 4) = Π_{j≤4} μ/(μ+j)`
(surviving four draws and no more is what the chain computes), so the test pins the
*formula* rather than a Monte-Carlo average. For μ = 1.2 this gives E[n] = 0.825,
P(n = 0) = 1/(μ+1) = 0.455, P(n ≥ 4) = 0.0135; for an M dwarf (μ = 1.6) E[n] = 1.020 and
P(n = 0) = 0.385; for an O star (μ = 0.02) E[n] = 0.0198. Most stars have no planets, a
minority have a handful, almost none are packed — the observed shape, from one line of
arithmetic.

**Bulk draw** — a 10 × 7 weight table (rows = spectral class, columns = bulk), each row
normalised into **weights once at module load** (a `Float64Array(70)`, no per-star work),
then `f_Z` and the state modifiers are applied and a CDF accumulated in a scratch array
per system (7 floats, reused). Weights, authored, not fitted:

| class | rock | ice | super | mini | gas | icegiant | dwarf |
|---|---|---|---|---|---|---|---|
| O | 0.00 | 0.00 | 0.00 | 0.00 | 0.55 | 0.25 | 0.20 |
| B | 0.00 | 0.00 | 0.05 | 0.10 | 0.50 | 0.25 | 0.10 |
| A | 0.08 | 0.10 | 0.15 | 0.20 | 0.27 | 0.12 | 0.08 |
| F | 0.22 | 0.12 | 0.20 | 0.15 | 0.13 | 0.08 | 0.10 |
| G | 0.26 | 0.12 | 0.20 | 0.14 | 0.10 | 0.07 | 0.11 |
| K | 0.28 | 0.12 | 0.22 | 0.12 | 0.08 | 0.06 | 0.12 |
| M | 0.36 | 0.10 | 0.28 | 0.10 | 0.01 | 0.02 | 0.13 |
| WD | 0.30 | 0.15 | 0.10 | 0.03 | 0.02 | 0.03 | 0.37 |
| RG | 0.10 | 0.18 | 0.15 | 0.15 | 0.22 | 0.12 | 0.08 |
| RGe | 0.14 | 0.24 | 0.15 | 0.12 | 0.17 | 0.10 | 0.08 |

The test pins the *emergent* numbers, not these weights: over 20 000 systems per class the
giant fraction rises with Z by a factor ≥ 3 between the halo and bulge metallicities,
M dwarfs average more planets than G, O/B average under 0.1, and no class produces more
than `MAX_PLANETS`.

### 4.5 Architecture: where the orbits go

```
R★_AU = R★/R☉ · 0.0046504
a_0   = max(0.012, STAR_CLEARANCE · R★_AU)          // 6 R★ → 0.028 AU for the Sun ✓
a_out = DISK_OUT_AU · sqrt(M★/M☉)                   // 40 AU at 1 M☉, 18 AU at 0.2 M☉
```

Draw `n` axes log-uniformly in `[ln a_0, ln a_out]`, insertion-sort ascending into the
record (n ≤ 12, one `Float64Array` and a scratch permutation — 12 elements, so the sort
is a dozen compares), then one repair pass for stability. **The axes are drawn and sorted
first**, before any other per-planet draw, so `p` in the §2.3 channel map is already the
planet's outward index when the bulk, mass and orbit channels are consumed:

```
r_H(i,i+1) = ((m_i + m_{i+1})/(3·M★))^(1/3) · (a_i + a_{i+1})/2      // mutual Hill radius
require    a_{i+1} − a_i ≥ K_HILL · r_H(i,i+1)                        // K_HILL = 6
else       push a_{i+1} out to the required separation
if         a_{i+1} > a_out → drop the planet (n decreases)
```

6 mutual Hill radii is compact-but-stable (long-term stability wants ~8–10; observed
Kepler multiples sit at 10–20), chosen so generated systems look full without colliding.
The record carries the mutual Hill radius **the repair used**, computed from the pair's
pre-push axes, so the separation invariant `a_{i+1} − a_i ≥ K_HILL · r_H` is exact rather
than true to within a push — that is the form the test pins over 60 000 systems.

Overflow-dropping is what keeps packed giant systems honest. Measured over those 60 000
systems the repair pushes in a small minority of them and drops in 8 (a planet pushed to
`a_out` and discarded), because a log-uniform draw over a 1430× span already spaces
neighbours ~1.9× apart on average while K_HILL needs only 1.5×: the mechanism is there
for the tight cases, and the invariant test is what pins it, not the anecdote. A
Jupiter-mass planet does need ~0.8 AU of clearance at 1 AU around a solar mass, so a
*deliberately* packed three-giant system is the case that loses its outer planet.

Then per planet:

```
e = eScale · e_max(bulk) · u²                       // u² biases toward circular
i = eScale · 3° · u                                 // degrees, small by construction
ω = TAU·u                                           // argument of periapsis
θ₀ = TAU·u                                          // phase at system time 0
P = sqrt(a³/M★) years                               // Kepler III, a in AU, M★ in M☉
```

`eScale = 0.2 + 1.6·hash01At(systemSeed, 0)` is **one draw per system**, applied to every
planet: systems are internally correlated, which is what real systems do (compact systems
are uniformly circular; excited systems are excited everywhere). `e_max`: rock 0.15,
ice 0.12, super 0.10, mini 0.12, gas 0.35, icegiant 0.25, dwarf 0.20.

The repair pass runs *after* the mass draws, since the Hill radius needs both masses — so
the order is: count → axes → bulks → masses → repair → e/i/ω/θ.

### 4.6 Insolation, temperature, refinement

```
S     = (L/L☉) / a²                                 // insolation in S⊕
Teq   = Teff★ · sqrt(R★/(2·a_M)) · (1 − A)^0.25     // a_M in metres
band  = 0 if S > 8 · 1 if S > 1.05 · 2 if S ≥ 0.35 · 3 otherwise
Tsurf = Teq + ΔT                                    // §4.2: runaway, thermostat, or base
```

Pin: Earth values (L 1, Teff 5772, R★ 1 R☉, a 1 AU, A 0.30) → Teq 254.6 K, matching the
published 255 K. The band boundaries **are** the habitable-zone insolation bounds
(`HZ_S_IN = 1.05`, `HZ_S_OUT = 0.35`), so `inHZ` and `band = 2` cannot disagree — one pair
of constants, two uses.

The **display type** is a refinement of the bulk by insolation band *and* by mass — a flat
table, which is what keeps a hot super-Earth from being labelled TERRAN, an airless rock
from being labelled DESERT, and a Mars-mass world in the habitable band from being called
habitable. Mass matters because atmosphere retention does: the Moon and Mercury have no
cycle to run, and Mars lost its.

| bulk \ band | 0: S > 8 | 1: 1.05 – 8 | 2: 0.35 – 1.05 | 3: < 0.35 |
|---|---|---|---|---|
| rock / ice / super, `M < 0.02` | LAVA | BARREN | BARREN | ICE |
| rock / ice / super, `0.02 ≤ M < 0.3` | LAVA | BARREN | DESERT | ICE |
| rock / ice, `M ≥ 0.3` | LAVA | DESERT **+ runaway** | TERRAN | ICE |
| super, `M ≥ 0.3` | LAVA | DESERT **+ runaway** | SUPER_EARTH | ICE |
| mini | ← MINI_NEPTUNE, all bands → | | | |
| gas | ← GAS_GIANT, all bands → | | | |
| icegiant | ← ICE_GIANT, all bands → | | | |
| dwarf | LAVA | DWARF | DWARF | DWARF |

Albedo and ΔT then come from the display type (§4.2), with the runaway override. `S` needs
no albedo — it is `L/a²` — so the band, the display type and the albedo are all known
before the temperature: **one pass, no iteration, no convergence question.**

A `hotJupiter` flag is set when bulk is gas/mini and S > 20 (readout and search only; not
a type). What the mass tiers buy, checked across band 2 of a solar-luminosity star:
TERRAN worlds hold 261 – 290 K from the inner to the outer edge (the thermostat at work),
SUPER_EARTH worlds 264 – 295 K, and sub-Mars-mass DESERT worlds fall 267 → 205 K across the
same band, because nothing is regulating them. That spread is the difference between a
habitable zone and a habitable planet, and it is why `terran` is a flag and not a band.

**Tidal locking**:

```
locked = (a < A_LOCK·sqrt(M★/M☉))  or  (S > 50)        A_LOCK = 0.30 AU
```

A locked world sets `rot = P` (which also removes its GEO node, §7.1) and gets a readout
flag plus the half-lit icon of §6.2. `S > 50` catches hot Jupiters, which are all locked.
The `sqrt(M★)` scaling is what makes the rule reproduce the real cases with one constant:

| system | M★ | L★ (repo law) | HZ (AU) | lock radius | HZ locked |
|---|---|---|---|---|---|
| TRAPPIST-1 | 0.090 | 0.0039 | 0.061 – 0.106 | 0.090 | **yes** (real: all seven are) |
| Proxima Cen | 0.122 | 0.0079 | 0.087 – 0.150 | 0.105 | **yes** (real: Proxima b) |
| Sun | 1.000 | 1.000 | 0.976 – 1.690 | 0.300 | no (real: Earth free, Mercury 3:2) |
| 0.30 M☉ | 0.300 | 0.063 | 0.244 – 0.423 | 0.164 | no (the borderline case, §14) |

**Habitable-zone flags** (the search's main target):

```
a_hz_in  = sqrt(L/HZ_S_IN)  AU   // Sun: 0.976
a_hz_out = sqrt(L/HZ_S_OUT) AU   // Sun: 1.690
inHZ     = (band == 2)           // identical to a_hz_in ≤ a ≤ a_hz_out by construction
terran   = inHZ and display ∈ {TERRAN, SUPER_EARTH} and 0.5 ≤ M ≤ 5 M⊕ and age > 0.5 Gyr
         and not runaway and not locked
```

`locked` excludes the tidally-locked M-dwarf worlds from the plain `terran` flag — they are
still habitable candidates and still searchable by temperature, but "terran" in this
project means an Earth analog, and a search that returns only free-rotating worlds is the
one a player expects. A separate `lockedHZ` flag keeps them findable.

### 4.7 Belts

Two belts maximum, inner (asteroid analog) and outer (Kuiper analog):

```
a_snow  = A_SNOW_K · sqrt(L/L☉)                          // 2.7 AU for the Sun ✓
inner:  a_b = a_snow · (0.55 + 0.40·u)                   // 1.5 – 2.6 AU for the Sun
        Δln a = 0.10 + 0.25·u        m_b = 10^(−4 + 2.5·u) M⊕   // 0.0001 – 0.079
outer:  a_b = a_out · (0.35 + 0.45·u)
        Δln a = 0.15 + 0.35·u        m_b = 10^(−2 + 2.0·u) M⊕
presence  P = clamp(0.90·fade(age) − 0.35·nGiantsInside, 0, 1)
fade(age)   = 0.25 + 0.75·exp(−age/1.5 Gyr)
```

`fade` is the debris-disk decline (fractional luminosity falls by ~an order of magnitude
over the first Gyr); `nGiantsInside` is the scouring by any gas/ice giant inside the belt
radius. A belt whose draw fails presence is not written at all — `belts.count` is 0, 1
or 2, never a zero-mass placeholder.

Belts are **not** resolved into bodies. Each carries a `typicalBody` = the Ceres-analog
constants (`R = 470 km`, `M = 9.4e20 kg`, ρ 2160 kg/m³, albedo 0.09), which is what the
delta-v map uses — the brief's "belt (dv simplify as typical asteroid without details)".
The stipple for drawing is `STIPPLE_N` angle/radius pairs hashed once per system into the
layer's preallocated arrays (§6.5), never per frame.

### 4.8 Moons

A count, not a system: `moons = floor(moonMax(bulk) · u³)` with moonMax 1 (rock/ice),
2 (super), 8 (mini), 80 (gas), 30 (icegiant), 0 (dwarf). It appears in the readout and
the search summary and affects nothing else — no moon orbits, no moon dv nodes. Justified
by cost: moons would need their own Hill-stability pass and their own icons, and the brief
does not ask for them. `moonMax` for giants is the real count scale (Jupiter 95, Saturn
146), so a readout of "34 moons" on a gas giant is credible.

### 4.9 The SystemRecord

Fixed capacity, struct-of-arrays, one instance owned by `planets.js` (module scope, like
`star-types.js`'s `calibrationRecord`) plus a second for the search's "currently open"
system if the UI ever needs two — 0.5.3 needs one.

```
star:    key, mass, lum, teff, rStar, age, metal, state, spec, colorIndex, absMag,
         component, R, distToArm, aHzIn, aHzOut, aSnow, aOut, name(32 bytes)   ≈ 200 B
planets: a, mass, radius, density, ecc, inc, peri, phase, period, teq, tsurf,
         insolation, rHill, rotHours, moons, bulk, display, flags
         → 14 × f64 + 3 × u8, × 12 planets                                 = 1152 B
belts:   a, dlnA, mass, mu, radius, stipple       → 4 × f64 + 1 × u32, × 2    = 96 B
counts:  planetCount, beltCount, terranCount, giantCount, maxPlanetMass,
          bulkHistogram(7 u8), typeHistogram(10 u8),
          bestTerran{A, Mass, Tsurf, Display}                             ≈ 1.5 KB total
env:     a, mass, teq, tsurf, display per planet, × 12 — the summary tier's
          per-planet window on the same walk (§4.10)                       ≈ 500 B
```

`flags` is `locked | hotJupiter | terran | inHZ | runaway | lockedHZ`; the last two are the
§4.6 runaway bifurcation and the "habitable but locked" findable case, so the search can
ask for either without re-deriving the band. A record is reused across calls, so every
field is either written or reset per `generateSystem` — the histograms and the four
`bestTerran*` scalars are explicitly zeroed at the top of the walk, which is what keeps a
reused summary from reporting the previous system's candidate. `stellarInputs` writes a
flat snapshot record (mass, luminosity, teff, rStar, age, metallicity, state, spec,
component, R, distToArm) that `generateSystem` consumes — the generator never re-derives a
star's own properties, so the summary and the full walk agree about them by construction.

Every field is derived in one `generateSystem(ref, snapshot, out)` call: ~120 hash draws,
~400 flops, no allocation. **Budget: < 20 µs**, measured over 10 000 systems; the shipped
figure is 1.6 µs median on this repo's test machine.

### 4.10 The summary tier

Search (§5) does not need orbits, phases, belts or moons — it needs "does this star have a
planet matching the filter". `planets.systemSummary(ref, snapshot, out)` computes only:

```
count, bulk histogram (7 u8), display-type histogram (10 u8),
best terran candidate {a, mass, tsurf, displayType}, maxPlanetMass, beltCount,
env: a, mass, teq, tsurf, display per planet (bounded by envCount)
```

The `env` block is §5.1's range filters reading the same walk: the values are the ones the
full record writes, per planet, in record order, so a summary answers
`tsurfMin/tsurfMax`, `teqMin/teqMax`, `planetMassMin/planetMassMax` and `aMin/aMax` without
ever becoming the full tier. It is written in both tiers and bounded by `envCount` rather
than reset, so a reused record never reads the previous system's rows.

Same channels, same draws, same results — a summary of a system and the full system always
agree, because the summary is the same walk with the orbit-field draws **and** their array
writes skipped. The counts (bulk histogram, type histogram, best-terran candidate,
`maxPlanetMass`) and the belt presence/width/mass draws all execute before the skip, and
the belt stipple seed is the only belt-side field a summary does not draw, because no count
reads it. That identity is a test pin, not a hope: `summary(p).typeHistogram ===
full(p).typeHistogram` for 5 000 random systems, along with every other count.

Cost target: **< 6 µs per star**, so a 300k-star galaxy scan lands under ~1.8 s worst case
and, with the star-filter stage running first (§5.3), typically far less. The shipped
figure is 1.1 µs median — the saving is not only the skipped writes: a one-planet summary
draws 8 channels instead of 14, and the count chain dominates both.

### 4.11 Designations

* Landmarks keep their name: `Sirius A`.
* Any other star: `S<key in base36, uppercase>` — e.g. `S1Y3K9P`. Stable across camera
  moves (it is the key), short enough for the readout, and it makes two stars never share a
  label.
* Planets take the IAU lowercase letters in order of `a`: `b, c, d, …` (never `a`), so
  `S1Y3K9P b`. Belts are `belt 1` / `belt 2` in radius order.
* The full designation is built into a reusable byte buffer, not concatenated per frame
  (`AGENTS.md`: no string concat in the frame loop). The readout is text at 4 Hz like
  `#overlay`; the system layer draws designations only for the hovered/selected body.

### 4.12 What a reimplementation must pin

* Two `generateSystem` calls with the same key give byte-identical records; a different
  `model.seed` gives a different system; the same key in a different galaxy is unrelated.
* No planet inside `STAR_CLEARANCE·R★`, none outside `a_out`, no pair closer than
  `K_HILL` mutual Hill radii (all three checked over 20 000 systems).
* `E[n]` matches the analytic geometric-chain mean within 2% over 100 000 draws.
* Earth values reproduce: a 1 M☉ / 1 L☉ / 5772 K star puts its HZ at 0.976–1.690 AU, its
  snow line at 2.7 AU, and a 1 M⊕ rocky planet at 1 AU at Teq 255 K, Tsurf 288 K.
* The six-body temperature pin of §4.2 (Mercury 433, Venus 742, Earth 288, Mars 216,
  Moon 270, Ceres 163) and the two locking pins (TRAPPIST-1 and Proxima HZ worlds locked,
  the Sun's not).
* The thermostat is monotone: across band 2, Tsurf stays inside 260–296 K for every
  TERRAN/SUPER_EARTH whatever the insolation — the habitable band is habitable — while
  sub-`ATM_RETAIN_M` worlds in the same band fall monotonically with distance.
* The giant fraction rises with metallicity by ≥ 3× between halo and bulge Z.
* WD systems are compact and debris-rich; giant-star systems have no planets inside the
  stellar radius.
* The summary tier equals the full tier's histograms.
* `generateSystem` allocates nothing (checked by running 100 000 calls with a heap-delta
  assertion: `global.gc()` on both sides, five trials, the median delta reported. A 16-byte
  object per call would show 1.6 MB, so half of that is a real leak and half is Node's own
  bookkeeping — the shipped median is 272 B over 100 000 calls).
* A per-block stellar-inputs path that the sort cannot drift: a procedural field star's
  snapshot equals a fresh `deriveStar` for the same key, a local gap-fill star equals the
  renderer's own `(slotSeed → deriveSeed)` derivation, and an object member equals
  `deriveStarWithAge` at its object's coeval age. This is the anti-drift pin: the
  generator must describe the star the renderer drew, for every block.

## 5. 0.5.2 — Search

New file `src/core/search.js`. Pure: it takes an accessor (`renderer.starBlocks()` +
`fieldBuffers()` + the selection set) and a filter struct, and writes into preallocated
result buffers. No DOM, no model.

### 5.1 Filters

Star predicates (all optional, AND-combined):

| field | values | source |
|---|---|---|
| `classes` | bitmask over `SPECTRAL_CLASSES` (10 bits) | `colorIndex` for catalog/landmarks, derived class for procedural |
| `states` | bitmask ms / giant / wd | derived |
| `lumMin`, `lumMax` | L☉ | derived |
| `massMin`, `massMax` | M☉ | derived |
| `distMin`, `distMax` | ly from the **camera** | record position |
| `components` | bitmask thin / thick / bulge / halo | `fieldBuffers().component`, or `density.rhoDecomposed` for the rest |

Planet predicates (any of these forces the summary tier):

| field | values |
|---|---|
| `planetTypes` | bitmask over the 10 display types |
| `terranOnly` | bool — the §4.6 flag |
| `tsurfMin`, `tsurfMax` | K |
| `teqMin`, `teqMax` | K |
| `planetMassMin`, `planetMassMax` | M⊕ |
| `aMin`, `aMax` | AU |
| `minPlanets` | int |
| `barrenOnly` | bool — `count === 0`, the explicit inverse of an empty `planetTypes` mask |
| `needsBelt` | bool |

A `planetTypes` mask of 0 means "no planet constraint", not "no planets" — the empty
filter must not silently return a galaxy of barren stars. "Stars with no planets" is a
separate explicit checkbox (`barrenOnly`).

### 5.2 Scope

```
scope = 'selection'   // the set, 1 … 256 stars — default whenever the set is non-empty
scope = 'galaxy'      // every resident record — the fallback when nothing is selected
scope = 'auto'        // the rule above, selectable: what the menu ships on
```

Exactly the brief's "in all galaxy (fallback if no selected)", with `auto` naming the rule
so a viewer can force the galaxy *with* a selection set. The UI shows which scope ran
(`scanned 300 128` vs `scanned 214`), so the fallback is never invisible: `stats.scope`
reports the resolved scope and `scanned` counts the records the filter actually saw — the
set's resident members under `selection` (a key that is not resident right now is never
scanned), every resident record under `galaxy`.

### 5.3 Two-stage scan, and the cost contract

Stage 1 runs the star predicates from the record alone where possible (`colorIndex`,
`absMag`, position) and from one `deriveStar` where not. Stage 2 runs
`planets.systemSummary` only for survivors. This is why a class filter over the whole
galaxy is cheap (no planet work at all for 90% of stars) and a habitable-world filter is
the expensive case.

Result buffers, allocated once:

```
MAX_RESULTS = 512
resKeys     Uint32Array(512)      resX/Y/Z  Float64Array(512)   // the record's own position
resSlot     Uint32Array(512)      resClass  Uint8Array(512)     // colour index, for the readout
resStar     Float64Array(512 × 5)   // mass, luminosity, teff, age, rStar — zero if no derivation ran
resBest     Float64Array(512 × 4)   // a, mass, tsurf, display of the matched planet
resCount    // filled
stats       { scanned, matched, truncated, msStage1, msStage2, scope }
```

`resStar` is written only when the filter ran a derivation (a mass or planet predicate);
a class-only query leaves it zero, because the record does not carry a mass and inventing
one would make the readout lie. `resBest` names the planet that satisfied the predicate —
for `terran` the star's best candidate, for a count-only query nothing.

Results are collected in scan order, then the first `MAX_RESULTS` matches are sorted by
distance from the camera ascending (nearest-first, the cell manager's rule) — sorting 512
entries is ~0.1 ms and keeps "show me the nearest Earth-like world" answerable without a
second query. `matched` counts every match, `truncated` says the list was cut.

Budgets, measured in `experiments/search-test.js` at 300k procedural stars:

| query | budget |
|---|---|
| star-only filter, galaxy scope | < 120 ms |
| planet filter, galaxy scope | < 600 ms |
| planet filter, selection scope (214 stars) | < 2 ms |

If the galaxy-scope planet scan misses its budget in measurement, the specified fallback is
**frame-chunked scanning**: `search.step()` processes up to `SEARCH_CHUNK = 20 000` stars
per frame from the loop, with `scanned/total` in the readout, and results appear as they
arrive. Do not build the chunking before the measurement says it is needed — that is the
repo's rule (measure, then decide), and the synchronous path is the one that stays simple
to test.

### 5.4 UI

A `Search` section in the settings menu, six rows, no new panels:

```
scope      [auto ▾]                 class   [any ▾]      ptype  [any ▾]
Tsurf      [    ] – [    ] K        ☐ terran only   ☐ has belt   ☐ no planets
[ Search ]  [ Add to selection ]  [ Clear ]
```

An empty Tsurf field is an unbounded side, not a zero. Any control change re-runs the scan
on commit, so the readout always answers what the menu currently says.

`Add results to selection` pushes the result keys into the set through the same
capacity/nearest-first rules as §3.2, so a search becomes a working set for a route in two
clicks. `N` / `Shift+N` cycle the primary through it; `V` opens the system view on the
current primary. Results are also listed in `#sysread` (top 12 lines: designation, class,
distance, matched planet, Tsurf), under a header line naming the scope, the scanned and
matched counts, whether the list was cut, and the scan's stage time.

### 5.5 Preset fields

`presets.js` `FIELDS` gains `search` (the filter as a compact token) and `scope`. The result
list and the selection are **not** preset state — they are transient, like the camera
position. The filter is, because it describes what the viewer asked for and a pasted preset
should reproduce the same query.

The token is `key=value` segments separated by `;`, emitted in a fixed order so two filters
with the same meaning serialize identically:

```
cls=G,K          spectral classes            st=ms,giant,wd   states
lum=0.1-100      L☉                          mass=0.5-1.5     M☉
dist=10-5000     ly from the camera          cmp=thin,thick   components
pt=terran,gas-giant   display types          ts=200-320  K surface
te=100-400       K equilibrium               pm=0.5-10   M⊕   a=0.5-5 AU
minp=3           at least N planets          flag=terran+belt+noplanets
```

A range is `lo-hi`, either side open (`ts=-320` is "up to 320 K"), an absent segment means
"no constraint", and `search` is omitted from the line entirely when the filter is empty.
The plan's first draft wrote the example positionally (`G,K|terran|220-300`); the shipped
grammar is the segment form, which survives a field being skipped — §11.1 records why.

## 6. 0.5.3 — The close-system schematic

New file `src/render/system-layer.js`, new canvas `#system` in `index.html` above
`#labels`, new `<pre id="sysread">` for the readout. Drawn every frame **only while the
system view is open**; otherwise `draw()` is one boolean test and a return.

### 6.1 Layout: log-polar

True-scale radii are unusable (0.03 AU to 40 AU is a factor of 1300), so the radial axis is
logarithmic — the same trick a real system diagram uses, and it makes an inner rocky system
and an outer giant system occupy comparable screen area:

```
a_in_view  = max(a_0·0.6, 0.008 AU)
a_out_view = max(a_out·1.2, outermost belt · 1.1)
ρ(a)       = (ln a − ln a_in_view) / (ln a_out_view − ln a_in_view)     ∈ [0,1]
r_px       = R_STAR_PX + ρ · (R_EDGE_PX − R_STAR_PX)
R_STAR_PX  = 34                    R_EDGE_PX = min(w, h)·0.46
angle      = θ(system time)        // see §6.4
```

Belt annuli map through the same `ρ`, so a belt and a planet at the same `a` sit at the
same radius — the diagram is a faithful ordering of the system even though the spacing is
compressed.

### 6.2 Draw order (back to front)

1. habitable-zone annulus: `ρ(a_hz_in)` … `ρ(a_hz_out)`, filled `rgba(96, 200, 128, 0.07)`,
   plus a 1 px `rgba(96,200,128,0.25)` outline — the one piece of "where could life be"
   that should be visible without being asked for.
2. orbit ellipses: one `ctx.ellipse` per planet at the star's centre, semi-major
   `r_px(a)`, eccentricity `e`, rotated by `ω`, vertically squashed by `cos i`; stroke
   `rgba(150,175,215,0.22)`, 1 px. An ellipse is drawn even when the planet is a dot on it,
   so a frozen system still reads as a system.
3. belts: `STIPPLE_N` dots per belt, `rgba(190,180,160,0.35)`, radius 1 px, at
   `(ρ(a_b + Δa·u), θ_belt(t) + φ_s)` with the stipple angles/radii hashed **once** per
   system into preallocated `Float32Array`s; the whole belt rotates at its own Kepler rate.
4. the star: filled circle, radius by state (ms 12 px, giant 20 px, wd 6 px), colour from
   `star-record.js` `CLASS_COLORS[colorIndex]`, plus a `rgba` halo at 2× radius.
5. planets: filled circles in the display-type colour (§4.2), radius from a **five-bucket**
   size ramp keyed on log mass — not on real radius, per the brief:
   `M < 0.1 → 3 px · < 2 → 5 px · < 20 → 7 px · < 100 → 10 px · ≥ 100 → 13 px`.
   Gas and ice giants get a 1 px ring at 1.7× radius; locked worlds get a half-filled disc
   (the star-facing half lit); terran-flagged worlds get a 1 px green outline.
6. selection: the selected body gets the label layer's ring colour
   (`rgba(255,215,94,0.8)`), radius +4 px; the hovered body gets a designation
   label, in the label layer's own type and halo. A belt has no single icon, so its ring is
   the circle its pick band measures against — the belt's own screen radius (§6.3).
7. routes and the ship icon, when 0.5.5 is active (§8.5).

All colours and fonts are module constants; all positions go into preallocated
`Float32Array`s (`planetScreenXY`, `beltStippleXY`). Per frame the layer performs
~12 ellipses + ~780 dots + ~15 circles ≈ 800 canvas ops — comparable to the label layer's
~60 `fillText` calls, well inside a 16 ms frame, and zero allocations.

### 6.3 Picking in the schematic

Trivial and exact: the layer already has every body's screen position, so a click is a
distance test against `iconRadius + 4 px`, nearest wins, belts are picked by
`|r_click − r_belt| < 6 px`. No projection, no camera. Clicking empty space clears the
system-view selection but does not leave the view (leaving is `V` / `Esc` / the button).

The bodies are the planets and the belts. The star is not selectable: it is the
schematic's centre, and neither §7's delta-v map nor §8's routes takes an endpoint on it,
so a ring around it would select nothing. A click is tested against the frame that is on
screen — the icons the last draw placed — and the pointer position rides the input state
that the star picker already reports (`pointerX` / `pointerY`, −1 off the canvas, over the
menu, or locked away), so the hovered designation needs no new event path.

### 6.4 Time in the system view — a separate control

The planetary phase is `θ = θ₀ + TAU·(t_sys/P)` with `t_sys` in years. **The galaxy's star
time slider does not drive it**, and the reason is arithmetic: at the slider's 1 Myr/s an
Earth-orbit planet completes 10⁶ revolutions per second — pure strobe, and at 60 Hz an
aliasing artifact that looks like a bug. `archive/0.4.0-plan-star-move.md` §3 analysed the
same class of problem for spiral winding; the answer there was to analyse rather than hide,
and here it is to separate the clocks.

So: `system time` is its own view control, exactly like wave damping (`archive/damping-plan.md`:
"a view control, like exposure, not a field of the galaxy model").

```
slider  −1 … 99  years/s, default 0 (frozen)     preset field `systime`
```

`-1` couples it to the camera fly speed the way the star-time slider does; `0` freezes;
`0.5 … 99` is years per second. The galaxy behind keeps running on its own Myr/s slider —
two clocks, two meanings, both visible in the readout. Nothing here writes to the model or
to the star buffer.

### 6.5 Enter / exit

* **Enter**: menu button `System view` or key `V`, requires a primary selection. On enter:
  generate the system (§4.9), hash the belt stipples, `flyToStar` if the camera is farther
  than 1 pc, switch the camera to `orbit object` on the star, disable fly translation keys
  (orbit keys still work — the viewer can look around the schematic's sky), show `#system`
  and `#sysread`.
* **Exit**: `V` again, `Esc`, or the button. The canvas is cleared on exit (the same rule
  `label-layer.setEnabled` follows: a canvas keeps its last frame, so hiding it must erase
  it), the camera keeps its orbit target, fly keys return.
* **The view tracks the primary.** The schematic *is* the primary's system, so a primary
  change while the view is open (`N`, a plain click) regenerates it, and clearing the
  selection (`X`, `R`, a model change) closes the view: a schematic whose star was
  deselected is a stale frame, and a canvas must never keep one.
* Menu rows gated to the view use a `data-view="system"` attribute, mirroring the existing
  `data-engine` mechanism, so rows that mean nothing outside the view are hidden rather
  than disabled.

## 7. 0.5.4 — The delta-v map

New file `src/math/deltav.js`: pure SI functions, `out` parameters, no allocations, no
state. Everything is closed form — no Lambert solver, no patched conics beyond a single
sphere of influence, no n-body. The brief's bar is "not precise … just realistic looking",
and the model below reproduces the published Solar-System map to a few percent, which is
far past that bar.

### 7.1 Nodes

Per planet, the nodes the brief lists, plus the two it was unsure about — both are in, and
both cost one line:

| node | radius | exists when |
|---|---|---|
| `SURFACE` | `R_p` | bulk is rock/ice/super/dwarf (giants have no surface: cloud-top only) |
| `LOW_ORBIT` | `R_p + h`, `h = max(200 km, 0.04·R_p)` | always |
| `GEO` | `a_geo = (mu_p/ω²)^(1/3)`, `ω = TAU/rot` | `rot < 1000 h` and `a_geo < 0.4·r_Hill` |
| `L5` | the planet's own `a`, 60° ahead | planet not locked to another body |
| `BELT_BODY` | the belt's typical body (§4.7) | per belt |

**GTO is not a node.** It is the transfer orbit between `LOW_ORBIT` and `GEO`, i.e. the
Hohmann dv already computed for that edge — the map labels that edge `GTO 3.9`. Adding a
GTO node would duplicate a number.

**C3 = 0 escape is a node**, because it is the hinge between planet-bound and star-bound
travel and every route in §8 crosses it: `dv_escape = (√2 − 1)·v_circ(r_lo)`, the
parabolic excess from low orbit. Earth: 0.414 × 7.79 = 3.23 km/s against the published
3.2. Skipping it would force routes to invent their own escape number, which is how two
numbers for the same thing start to disagree.

### 7.2 The closed forms

```
mu(M)              = G·M
v_circ(r)          = sqrt(mu/r)
v_esc(r)           = sqrt(2·mu/r)

SURFACE → LOW_ORBIT   dv = LAUNCH_LOSS·v_circ(r_lo) + DRAG[atm]
                      LAUNCH_LOSS = 1.20 (gravity + steering), DRAG in km/s:
                      none 0 · thin 0.15 · breathable 0.35 · thick 0.80 · H/He 1.50
                      (atm is the display type's atmosphere column, §4.2)
LOW_ORBIT → GEO       dv = [v_circ(r_lo)·(sqrt(2·a_geo/(r_lo+a_geo)) − 1)]
                         + [v_circ(a_geo)·(1 − sqrt(2·r_lo/(r_lo+a_geo)))]
LOW_ORBIT → ESCAPE    dv = (sqrt(2) − 1)·v_circ(r_lo)
LOW_ORBIT → L5        dv = dv_escape + L5_PHASE·v_orb_star,  L5_PHASE = 0.02
                        t  = L5_PHASE_FRACTION·P_orb,        fraction 0.25
                        (the 60° drift is time, not energy — a low-thrust spiral)

star-centred, a1 → a2, coplanar circular, direct (no assists):
  v_orb(a)  = sqrt(mu★/a)
  dv_dep    = |v_orb(a1)·(sqrt(2a2/(a1+a2)) − 1)|
  dv_arr    = |v_orb(a2)·(1 − sqrt(2a1/(a1+a2)))|          // = v_inf at encounter
  t_H       = π·sqrt(((a1+a2)/2)³/mu★)

capture into the target's low orbit, from v_inf:
  dv_cap       = sqrt(v_inf² + 2·mu_p/r_lo) − v_circ(r_lo)      // kill the excess, then circularise
  dv_arr_orbit = max(0, dv_cap·(1 − AERO_FRACTION[atm]))
                 AERO_FRACTION: none 0 · thin 0.40 · breathable 0.60 · thick 0.70 · H/He n/a
LOW_ORBIT → SURFACE   dv = max(DEORBIT_DV, dv_launch·(1 − LAND_CREDIT[atm]))
                      DEORBIT_DV = 0.15 km/s
                      LAND_CREDIT: none 0 · thin 0.65 · breathable 0.98 · thick 0.95 · H/He n/a
                      (a H/He world has no surface node, so the landing form never sees it)
```

Node-to-node cost across two planets is the chain through the star:

```
dv(A→B) = dv(A → A.LOW_ORBIT if starting on the surface)
        + dv_escape(A)                     // leaves A's sphere of influence at v_inf ≈ 0
        + dv_dep(a_A → a_B)                // star-centred Hohmann
        + dv_arr_orbit(B)                  // capture into B's low orbit
        + dv(B.LOW_ORBIT → B.SURFACE)      // if the destination is a surface
```

`dv_escape(A)` plus `dv_dep` is the standard patched-conic composition: escaping with
C3 = 0 and then burning `dv_dep` at the star's distance is what a real mission profile
does, and it is why the numbers below land where they do.

Two consequences worth stating because they read as surprises:

* **Small bodies are expensive to reach.** A belt body has almost no gravity well, so
  `dv_cap ≈ v_inf` — nearly the whole arrival speed must be killed propulsively. LEO → Ceres
  transfer orbit is 6.31 km/s and capture adds 4.57 more. That is real (Dawn needed ion
  propulsion), and it is why §4.7 gives belts one typical body instead of a resolved
  population.
* **Super-Earths have deep wells, and the asymmetry is arrival vs departure.** The 4.2 M⊕ /
  1.53 R⊕ world of §6.6 has `v_circ = 12.9 km/s` at low orbit, so leaving its surface costs
  16.2 km/s against Earth's 9.7 — while *arriving* is cheap, because aerocapture and the
  thick-atmosphere landing credit absorb most of the well (1.62 + 0.81 km/s in that
  example). A route that lands on a super-Earth and takes off again pays for the well twice,
  and the report says so.

0.815 M⊕/0.723 AU/thick; Ceres as the belt body) and asserts against published values:

Structural invariants on the same real bodies:

* **Earth has a GEO node**: `a_geo = 42 163 km < 0.4·r_Hill = 598 573 km`.
* **The Moon has none**: `a_geo = 88 434 km > 0.4·r_Hill = 24 605 km` — a synchronous body's
  geostationary radius is outside its own Hill sphere, which is exactly why the rule is
  `a_geo < 0.4·r_Hill` and not a rotation-period check alone.
* There is **no LEO → low-Moon-orbit pin**. Moons are counts (§4.8), not bodies, so the
  model has no satellite node and the published 3.26 km/s figure (which uses a low-energy
  Lagrange-point route this model excludes by design) is not comparable. Recorded here so
  nobody adds it later and then "fixes" the model to match.

Plus invariants on generated (procedural) systems: every dv ≥ 0; outward transfers cost
more than inward ones at equal |Δa| (the Oberth-free symmetry check is `dv_dep(a1→a2) =
dv_arr(a2→a1)` at equal radii); `t(dv)` monotone non-increasing; `t(dv_min) = t_H`
exactly; `t → 4d/dv` as `dv → ∞`.

If a tolerance fails, the constant is wrong, not the tolerance — `LAUNCH_LOSS`,
`AERO_FRACTION` and `L5_PHASE` are the only authored numbers in the file, and each has a
physical meaning stated next to it.

### 7.4 Travel time at an energy budget

The brief's "average time to economy travel with selected energy budget". Minimum-energy
(Hohmann) is the cheapest and slowest; spending more dv shortens the leg. Two limits
bracket it:

```
d       = π·(a1 + a2)/2 · AU      // metres; the Hohmann half-ellipse, i.e. the path flown
dv_min  = the map's own LEO→LEO number (§7.2 chain)      t_min = t_H
dv_x    = 4·d/t_H                 // the dv at which a constant-acceleration leg beats the ellipse
s       = clamp((dv_leg − dv_min)/(dv_x − dv_min), 0, 1)
t_brach = 4·d/max(dv_leg, dv_x)   // accelerate half, flip, decelerate half:
                                  // t = 2·sqrt(d/a), dv = 2·sqrt(a·d) ⇒ t = 4d/dv
t(dv)   = t_H·(1 − s) + t_brach·s
```

`d` is the **arc**, not the radius gap `|a2 − a1|`. That choice is the whole calibration:
with the radius gap, `dv_x` for Earth→Mars comes out at 14 km/s — inside a chemical tank —
and a 1 g ship reads 2.1 days, both of which flatter the model into nonsense. With the arc,
`dv_x = 106 km/s`, a chemical tank cannot reach it, and the times land where the
torchship literature puts them.

Properties, all pinned by test: `t(dv_min) = t_H` exactly (s = 0); `t` is continuous and
monotone non-increasing in dv; for `dv_leg ≤ dv_x` the leg is **exactly** `t_H` whatever the
budget — `t_brach` is clamped at `dv_x`, so extra dv below the crossover buys nothing; for
`dv ≫ dv_x` it converges to `4d/dv`. That flat region is not a defect, it is the model
saying out loud what a chemical rocket is: you cannot buy your way out of an ellipse.

Earth → Mars, computed (`d = 3.964 AU = 5.930e11 m`, `t_H = 258.8 d`, `dv_min = 5.04 km/s`,
`dv_x = 106.1 km/s`):

| ship | budget 1 dv_leg | accel limit | s | time |
|---|---|---|---|---|
| chemical (3 m/s², 20 km/s) | 20 km/s | — | 0.15 | **258.8 d** (no gain, below `dv_x`) |
| nuclear (1 m/s², 40 km/s) | 40 km/s | — | 0.35 | **258.8 d** |
| generation (0.001 m/s²) | 48.7 km/s | accel | 0.43 | **258.8 d** (below `dv_x`, no gain) |
| fusion (0.3 m/s²) | 843.6 km/s | accel | 1.00 | **32.5 d** |
| stardrive (10 m/s²) | 4 870 km/s | accel | 1.00 | **5.6 d** |

The stardrive row is the classic "1 g to Mars in under a week", reached from the same
formula with no special case, and the first two rows are why the brief separates
"conventional rockets inside star system" from "some sci-fi engine": tank size is nearly
irrelevant, acceleration is everything.

The generation row is worth a sentence because it reads as a bug and is not one. At
0.001 m/s² its ceiling on this leg is 48.7 km/s — below the 106 km/s crossover — so it flies
the same ellipse as a chemical hull and buys no time inside a system, despite having 300× the
dv. That is the correct answer for the class: a generation ship is not an in-system runner,
it is an endurance vehicle (§8.3), and its tank takes **190 years** to burn at its own
acceleration, which is precisely why the brief asks for it only between stars.

The energy budget is a slider, `budget ∈ [0,1]` (preset field `budget`, default 0.35),
mapped **logarithmically** so the low end stays usable when a ship's ceiling is four orders
of magnitude above the minimum:

```
dv_ceiling = min(2·sqrt(ship.accel·d), ship.dvRemaining)     // what this engine can do here
dv_leg     = dv_min·(dv_ceiling/dv_min)^budget               // budget 0 → dv_min, 1 → dv_ceiling
```

`2·sqrt(a·d)` is the brachistochrone dv this leg's distance allows at the ship's
acceleration; the tank is the other bound. At `budget = 0.35` on the Earth→Mars leg a
fusion ship spends `5.04·(843.6/5.04)^0.35 = 30 km/s` and still flies the ellipse in
258.8 days — the slider reads as "how much of the engine are you willing to burn", and the
answer below `dv_x` is honestly "it changes nothing".

The same `s` scales the **departure wait**: `t_wait_effective = t_wait·(1 − s)`. The more
energy you buy, the less you care about planetary alignment — one blend factor, two
consequences, no second model. Chemical rockets come out dv-limited and window-bound (they
wait for the synodic alignment of §8.4), fusion and stardrive ships come out
acceleration-limited and window-free (§8.2), and that split *is* the gameplay the brief
describes.

### 7.5 The map UI

Drawn on the same `#system` canvas, toggled by `Delta-v map` (key `B`) inside the system
view:

* **Graph**: star at the left; planets in columns ordered by `a`; each column stacks its
  nodes vertically (surface, low orbit, GEO, L5) with `ρ`-independent spacing; edges are
  straight lines labelled in km/s to 0.1; belts are one column with a single node. This is
  the recognisable shape of a published delta-v map, which is the point — a viewer who has
  seen the Solar System one reads this immediately.
* **Table**: for the selected body, one row per node pair from the primary's low orbit:
  `dv km/s · t at budget 0 · t at the current budget · ship feasibility`.
* Edges and rows recompute only when the system, the budget or the ship class changes —
  a `dirty` flag, not a per-frame recompute. The graph itself is redrawn per frame (cheap,
  and the ship icon moves over it).

## 8. 0.5.5 — Ships, routes, autopilot

New file `src/core/route.js`. Like `search.js`: pure state and arithmetic, DOM glue in

### 8.1 Ship classes

One flat table — the brief's "conventional rockets inside star system and some sci-fi
engine or oversized Generation ship between stars":

| class | accel (m/s²) | dv (km/s) | v_cruise | 2·v_cruise | cargo (t) | crew | life support (y) | domain |
|---|---|---|---|---|---|---|---|---|
| chemical | 3 | 20 | — | — | 20 | 6 | 2 | in-system |
| nuclear | 1 | 40 | — | — | 80 | 12 | 4 | in-system |
| fusion | 0.3 | 12 000 | 0.02 c | 11 992 | 2 000 | 40 | 30 | in-system + nearby stars |
| stardrive | 10 | 200 000 | 0.10 c | 59 960 | 20 000 | 200 | 200 | interstellar |
| generation | 0.001 | 6 000 | 0.005 c | 2 998 | 1 000 000 | 5 000 | ∞ | interstellar |

A second consistency number falls out of `dv/a`, the time to empty the tank at full
acceleration: chemical 1.9 h · nuclear 11 h · fusion 1.27 y · stardrive 0.63 y · generation
**190 y**. The generation figure is the class in one number — it never stops burning — and
`route-test.js` asserts all five against `ship.dv/ship.accel`.

The `2·v_cruise` column is not decoration — it is the invariant **`ship.dv ≥ 2·ship.v_cruise`
for every interstellar class**, asserted by `route-test.js`. An interstellar leg spends
`dv = 2·v_cruise` (accelerate, decelerate), so a class that violates the inequality cannot
reach its own cruise speed and the table is lying. The generation ship sits closest to the
line on purpose: it spends half its budget getting there and has nothing for a return, which
is what a one-way colony ship is.

`v_cruise` is used only by interstellar legs (§8.3). Life support decides whether a leg is
*survivable*, which is what makes the generation ship the only honest answer to a
kiloparsec — and what makes the galaxy's scale legible: 1 kpc at 0.005 c is 652 000 years.

### 8.2 In-system legs

The §7.4 blend, with one extra feasibility check that separates the classes:

```
a_required = dv_leg²/(4·d)          // the constant accel a brachistochrone leg needs
feasible   = dv_leg ≤ ship.dvRemaining  and  a_required ≤ ship.accel
```

For a chemical ship on Earth→Mars, `a_required = 5040²/(4·5.930e11) = 1.1e-5 m/s²` —
nothing, so chemical ships are dv-limited and their ceiling is the tank. A fusion ship's
12 000 km/s tank would need `a_required = 60.7 m/s² > 0.3`, so it is accel-limited: the leg
is flown at `2·sqrt(0.3·d) = 843.6 km/s` and takes 32.5 days. The two limits compose into
one number, `dv_ceiling` of §7.4, and which one binds is what separates the ship classes.

### 8.3 Interstellar legs

Between two stars at distance `D` (from their snapshot positions, kpc → m):

```
v_cruise = min(ship.v_cruise, c·0.2)          // hard cap; relativistic treatment is out of scope (§13)
t        = D/v_cruise + v_cruise/ship.accel   // accelerate to cruise, coast, decelerate
dv       = 2·v_cruise
```

Computed with the table above:

| leg | fusion | stardrive | generation |
|---|---|---|---|
| 10 ly | 501 y | 100 y | 2 048 y |
| 1 kpc | 163 000 y | 32 600 y | 652 000 y |

These are the numbers the readout shows, unrounded, in years — no attempt to make them
comfortable. A generation ship crossing the disc takes longer than the disc is old as a
spiral, which is a feature: it tells the player why the brief pairs interstellar travel with
"oversized Generation ship" rather than with a faster engine.

### 8.4 Routes

`buildRoute(startRef, endRef, shipClass, budget, out)`:

* **Endpoints** are nodes, not stars: the viewer picks a start node and an end node from
  the delta-v graph (inside one system), or two stars (interstellar, which expands to
  `start.LOW_ORBIT → escape → interstellar → capture → end.LOW_ORBIT`).
* **Leg chain**, cap 16, preallocated: surface launch (if any) → escape → star transfer →
  capture → landing (if any). Interstellar routes insert the cruise leg.
* **Two-way route** (the brief's "transport or trade"): the outbound chain, a turn-around
  layover (`LAYOVER_Y = 0.25 y`, one authored constant), then the reverse chain — with the
  **synodic wait** on the return for low-energy legs:

```
P_i   = sqrt(a_i³/M★) years                     S = 1/|1/P1 − 1/P2|        // synodic period
φ_req = π·(1 − 2·t_H/P2)                        // Hohmann launch phase angle
φ_now = θ2(t_sys) − θ1(t_sys)                   // from the planets' own phases (§4.5)
t_wait = ((φ_req − φ_now) mod TAU)/(TAU/S) · (1 − s)
```

  The factor 2 in `φ_req` is the one that is easy to get wrong: during the transfer the
  target sweeps `2π·t_H/P2`, and it must be *at opposition* (π from the departure point)
  when the ship arrives, so it starts at `π − 2π·t_H/P2`. For Earth→Mars that is
  `π(1 − 2·0.377) = 44.4°` against the published 44° launch-window angle — pinned, with
  `S = 779.9 d` against the published 780 d. Mean wait over uniformly distributed starting
  phases is `S/2 = 390 d`, max `780 d` — the real 26-month window. At `s = 1` (a
  high-energy ship) the wait is 0, which is the point: energy buys freedom from astronomy.
* **Report**: per-leg `(dv, t, wait)`, totals, feasibility per ship class, and
  `roundTripYears`. The readout shows the whole chain as a small indented list.
* **One-way autopilot** (the brief's "setup single ship 1-direction autopilot"): the same
  chain flown once, with the ship advancing along it.

### 8.5 Autopilot

`routePosition(out, route, t)` — closed form, no integration, in keeping with the whole
engine:

* Each leg stores `(t_start, t_end, kind, a1, a2)`. Find the leg by binary search over 16
  entries, then `f = (t − t_start)/(t_end − t_start)`.
* For a Hohmann leg the position is the transfer ellipse: mean anomaly
  `M = π·f` → **`OrbitLib.solveEccentricAnomaly`** (already in the codebase for the
  apocenter engine) → true anomaly → `(r, θ)` in the system plane. Reusing that solver is
  deliberate: one Kepler solver in the repo, not two.
* For a brachistochrone leg the position is the constant-acceleration parabola along the
  chord: with `a·T² = 4·d` for the leg, `x(f) = 2·d·f²` while `f ≤ 0.5` (accelerating) and
  `x(f) = d − 2·d·(1−f)²` after the flip — `x(0.5) = d/2` and `x(1) = d` by construction.
  Visually distinct from the ellipse, which is honest about what the ship is doing.
* Waiting legs hold the ship at the departure node.
* The ship is drawn on the `#system` canvas as a 5 px triangle in the class colour with a
  dashed route polyline behind it, and `#sysread` shows
  `route  chemical · leg 3/5 (Mars capture) · 41 d remaining · dv spent 12.4/20 km/s`.
* Autopilot time uses the **system time** clock (§6.4) in years, so a route flown at
  10 y/s is watchable and at 0 is inspectable.

### 8.6 Minimal economy (last milestone, droppable)

The brief mentions transport/trade as the *purpose* of a route, not as a simulation. One
table and one function, no markets, no prices over time:

```
rockyFraction = (bulk ∈ {rock, ice, super, dwarf}) / planetCount      // 0 for a giant-only system
iceFraction   = (bulk ∈ {ice, dwarf} or beltCount > 0) / planetCount
priceIndex(system, good) — a deterministic function of the system's own composition:
  rock/volatiles   1 + 2·(1 − rockyFraction)         // a giant-only system pays for rock
  fuel (He-3/H2)   1/(1 + 0.5·gasGiantCount)         // cheap where the giants are
  water            1 + 2·(1 − iceFraction)
profit = cargo·(price_end − price_start) − dv_spent·FUEL_PRICE_PER_KMS
```

`FUEL_PRICE_PER_KMS = 0.02` per km/s per tonne, one authored constant. The route report
gains one line (`profit 1.8× at 24 t`). If the series runs out of room this milestone is
cut whole and nothing above it changes — that is why it is last.

### 11.1 Deviations from the plan as built

Places where the shipped code differs from the plan above, recorded so a reimplementation
from this file alone matches what exists:

* **`core/star-set.js` loads *before* `core/selection.js`.** The task table lists
  selection first, but `createSelection` reads `StarSet.STAR_SET_CAPACITY` at construction
  to preallocate the radius-select result, so the set module must already be on the page.
  `index.html` and `m1-smoke-test.js` both enforce that order.
* **§3.6's readout is a `#selection` `<pre>`, not two more `#overlay` lines.** The overlay
  is transient, 4 Hz refresh state; `selrad` and `selstars` are serialized into the preset
  line (`prompt: false`), so what the viewer reads and what a preset stores have to be the
  same thing. A dedicated `<pre>` beside the menu carries it and is hidden when the
  selection is empty.

And five where the shipped 0.5.1 differs from the plan above, recorded the same way:

* **The moon count has its own channel range (128 + p), not a 9th slot in the planet's
  8-wide row.** The §2.3 table first listed "rotation period + moon count" on one row, but
  a moon count drawn from a channel the rotation period already consumes is a shared draw —
  and putting it at `40 + 8·p` (the obvious spare slot) collides with the *next* planet's
  bulk-class channel, which is what the shipped code did first. One channel each in the
  128–199 gap, past the twelve planet slots, with a test that claims the whole map into one
  set and fails on the first duplicate.
* **Belt stipple seeds are the raw word of channel 204 / 214, and the dots are hashed on
  that seed, not on `systemSeed`.** §2.3's "300 + s" row reads as a channel of the system
  seed, which would make the two belts' 768 dots share one channel range and the inner
  belt's `stippleSeed` field meaningless. A belt therefore carries a seed of its own and
  `hash01At(stippleSeed, 300 + s)` produces the §6.5 angle/radius pair s.
* **Mass inside a bulk range is drawn log-uniformly.** §4.3's table gives the ranges but
  the draw was unspecified; the ranges span 100 (the dwarf bulk alone), so a linear draw
  would never produce a small body. Stated in §4.3 now.
* **The density pin is `5 M⊕ → 6730 kg/m³`, not "15 M⊕ → 5480".** The draft's third
  hand-check was computed with a different radius law than the table ships, and the
  cross-check it names (α Cen Bb, 5550 kg/m³) is not 15 M⊕. What the shipped law does put
  near α Cen Bb is a 1.13 M⊕ super-earth at 1.07 R⊕, 3 % off the observed 1.04 — stated as
  the pin instead.
* **§4.5's "three giants cannot fit inside 40 AU" aside is wrong and is not pinned.** Two
  Jupiter-mass neighbours need ~1.5× spacing, which a log-uniform draw over the 1430×
  `[a_0, a_out]` span already provides; measured over 60 000 systems the repair pushes in
  a small minority of systems and drops in 8. The invariant test (no pair closer than
  K_HILL mutual Hill radii, over 60 000 systems) is what pins the mechanism.

* **The stipple band is centred on `a_b` in log space, not written out from it.** §6.2 item 3
  puts the dots at `a_b + Δa·u`, but the record carries `dlnA` — a width in *ln* a, from
  §4.7 — and a belt is drawn as `a_b·exp(dlnA·(2u−1))`, so the dots fill `[a_b·e^{−dlnA},
  a_b·e^{+dlnA}]` symmetrically about the belt's own axis.
* **The channel halves are angles then radii, and the belt's start angle is one channel
  past the pairs.** The §11.1 bullet above names `hash01At(stippleSeed, 300 + s)` for
  `s = 0…2·STIPPLE_N−1`; the shipped split is `300+s` for the angle and `300+STIPPLE_N+s`
  for the radius of stipple `s`, with the belt's phase at `t = 0` at `300 + 2·STIPPLE_N` —
  the record has no belt-phase field, and one extra channel past the pairs keeps the
  start angle deterministic without growing it.
* **The clock is a property of the view, and `sysview` rides the preset line only.**
  `advance` is a no-op while the view is closed, so the years a system accumulates are the
  years the viewer spent looking at it; and `sysview` is applied by `applyPreset` (after the
  selection it needs), never by `readParams` — boot restores no selection either, so the URL
  field would only ever name a view with nothing open in it. `systime` is both.

And six where the shipped 0.5.3-4 differs from the plan above:

* **The star is not a selectable body.** §6.3 reads as "every body's screen position", but
  §7's delta-v map and §8's routes take no endpoint on the star, so selecting it would ring
  a body no later task can route to. Bodies are the planets and the belts; a click on the
  star's icon is empty space. §6.3 says so now.
* **A belt's selection ring is its own screen radius, not "icon radius + 4 px".** §6.2
  item 6's ring rule is written for an icon. A belt has none, so its ring is the circle its
  6 px pick band measures against.
* **The hover is recomputed at the end of each draw, against that frame's icons, and the
  per-body designation is cached at system entry.** A pointer sweep therefore changes two
  integers and one string reference — §4.11's "no string concat in the frame loop" holds
  across the sweep. A belt's hovered label sits where the pointer crosses its band, not at
  an icon that does not exist.
* **A pick is refused until a full draw has laid the system out.** The click is tested
  against the frame that is on screen, so the layer keeps one `layoutValid` flag that a new
  system clears — otherwise a click on the frame a view opened would be tested against the
  previous system's icons.
* **The click belongs to the schematic while it is open, and the pointer position rides the
  input state.** `state.pointerX/pointerY` are canvas-local CSS pixels (the star picker's
  own space), −1 off the canvas, over the menu, or under a locked cursor; the schematic's
  click routing displaces `selection.pickAny` for that click.
* **The headless test file landed with 0.5.3-4, not as 0.5.3-6's own step.** The stub-context
  harness had been rebuilt ad hoc for -2 and -3; making it permanent was what picking
  needed to be verified against ("the pick returns the body the draw placed"), so
  `experiments/system-layer-test.js` now covers the whole §6 draw contract at 39 checks and
  `run.py` runs it between `search` and `tile-stream`.

### 11.3 Measured: the search at 300 000 records

From `experiments/search-test.js` (`experiments/logs/search.json`), SBb, seed 3:

| path | cost | budget |
|---|---|---|
| class filter, galaxy scope (one record byte per star) | 1.2 ms median | 120 ms — inside |
| mass filter, galaxy scope (one `deriveStar` per star) | 110 ms median | inside, but 90× the class filter |
| planet filter (`terran`), galaxy scope (summary walk on survivors) | 248 ms median | 600 ms — inside |
| planet filter, 214-star selection scope | 1.5 ms median | 2 ms — inside |

The scan reads **stored** positions, like `selectAround`: a query is a property of the
model's stars, not of this instant's rotation, so the answer is stable while the camera
moves, and the distance bounds are the only camera-dependent part. Stage separation is what
buys the 1.2 ms class filter — the record's colour index, magnitude byte and position
answer a class, state, luminosity or distance query with no derivation at all, and stage 2
never runs (the test pins `msStage2 === 0` for it). A mass filter is the honest exception:
the record does not carry a mass, so every star costs one `stellarInputs`, and it lands at
110 ms of the 120 ms budget — which is why the mass filter is the one case 0.5.2's frame
chunking was designed for, and why the budget is met before it is needed (0.5.2-5 is not
built). The 214-star selection scope is the path a viewer actually repeats: two orders of
magnitude under budget.

## 12. Known limits

Stated up front so nobody later mistakes them for bugs, in the same spirit as
`archive/0.4.8-plan-realistic-3d-shapes.md` §8:

* **The habitable zone inherits the repo's mass–luminosity law.** `luminosityFromMass` is a
  piecewise power law (α = 2.3 below 0.7 M☉), which over-luminates late M dwarfs: at
  0.09 M☉ it gives 0.0039 L☉ against the real 0.0005, so a generated TRAPPIST-1 analog
  puts its HZ at 0.061–0.106 AU instead of 0.022–0.039 AU — 2.7× too far out. This is the
  existing population law, not a new error, and changing it would move star colours, the
  exposure calibration and the 0.4.5 giant branch, i.e. 0.3/0.4 territory. Recorded, not
  fixed here; the locking rule still fires correctly because it scales with `sqrt(M★)`,
  not with L.
* **The gas-giant mass–radius law is radius-saturating, and therefore wrong at both ends of
  the sub-Jovian range.** With `p = 0.05` anchored at Jupiter: Jupiter is exact (11.2 R⊕,
  ρ 1248 against 1330), Saturn is 15% too large (10.5 against 9.1 R⊕), and a 10 M_J planet
  is ~30% too large. A single power law cannot be flat above 1 M_J and steeper below it.
  Radius feeds only the readout's density and the icon bucket (§6.2), so the schematic is
  unaffected.
* **Coplanar, circular, no assists.** Every star-centred transfer assumes the two orbits are
  coplanar and circular, so real inclinations (which cost ~0.1–2 km/s) are missing and
  gravity assists (which the brief excludes) are absent. Generated inclinations are drawn
  (§4.5) and shown, but the delta-v map ignores them — a deliberate inconsistency, because
  a plane-change term would make the map noisy without making it useful.
* **Super-Earth greenhouse terms are unconstrained by data.** The 40 K base for
  SUPER_EARTH and its share of the thermostat are authored; no such atmosphere has been
  characterised. The pin is only that the branch is monotone and bounded (§4.12).
* **The brachistochrone blend is not a trajectory.** `t(dv)` interpolates between a Hohmann
  ellipse and a constant-acceleration flip; no real conic sits in between. It is monotone,
  exact at both ends and cheap, which is what the brief's "realistic looking" asks for.
  The constant-acceleration branch also ignores the destination's orbital velocity (a real
  intercept must match ~30 km/s of tangential motion), which is why it is gated behind
  `dv_x` and why `d` is the arc rather than the radius gap: both choices push the answer
  toward the conservative side of the published torchship figures rather than the
  optimistic one. One consequence: any class whose acceleration ceiling falls below `dv_x`
  never beats the ellipse in-system, however large its tank (the generation row of §7.4).
* **One snapshot per selection, so a picked star's props are frozen at pick time.** An age
  change re-derives the set (§3.2); a *model* change clears it. A star whose properties
  change for any other reason (there is none today) would show stale numbers.
* **Belts are a ring of dots, not a population.** No size distribution, no collisional
  cascade, no resonant gaps. The typical body is a Ceres analog for every belt in the
  galaxy, which is exactly the simplification the brief asked for.
* **Picking a moving star costs one dispatched `orbitPosition` per record.** Measured at
  55 ms for 300k records (plan §11.2) — over the 16 ms click budget — while the frozen-sky
  fast path is 3.2 ms. The plan's remedy is the view-axis pre-reject specified in §3.1 (a
  coarse reject by the star's screen-space distance from the click axis before any
  dispatch), *not* a spatial index: the buffer is rewritten per frame anyway, so an index
  would be rebuilt as often as it is queried. Until then a click on a moving sky drops
  about three frames, which is invisible next to the residency work the same click waits
  on.
* **Under the simple engine, the picked position is the baseline, not the pixel.** The
  simple engine evolves field-star azimuths on the GPU, so the CPU has no copy of that
  state and `engineRecordPosition` falls back to the identity/classic baseline plus the
  apocenter pass. `recordPositionApproximated()` reports exactly that (the test pins it for
  masks 2/3/6/7), and the label layer's rings use the same fallback, so the visible
  selection follows the CPU model rather than the rendered pixel. The gap closes with
  `movement-parity-plan.md`.

## 13. Out of scope

* **Relativity.** Nothing above ~0.2 c is modelled; `v_cruise` is capped there. Time
  dilation, relativistic rocket equations and mass-ratio budgets are all outside a
  "realistic looking" bar.
* **Gravity assists, plane changes, low-thrust spirals, Oberth bonuses at periapsis.**
  Every transfer is direct and coplanar, as the brief specifies.
* **Moons and satellites as bodies or delta-v nodes.** §4.8 gives a count only, so there is
  no low-lunar-orbit edge and no Lagrange-point route through a moon (§7.3 records why the
  published LEO→Moon figure is not a pin). L5 nodes are of the *planet–star* pair.
  Rings, atmospheres as a simulation, weather, terrain and landing-site selection are out
  for the same reason.
* **Real exoplanet catalogs.** No NASA Exoplanet Archive import, no authored systems.
  Every planet is hash-derived; the Solar System appears only as a test fixture.
* **Planet rendering in 3D.** No spheres, no textures, no new render path, no WGSL (§1.1).
* **Star-buffer or record changes.** `StarPacked` stays 16 bytes; `UNIFORM_FLOATS` and the
  `CameraUniform` layout do not grow.
* **A live economy, factions, missions, saving routes to disk.** §8.6 is a price index and
  one line of text.
* **Multi-star systems.** Binaries are real and common (~25% of solar-type stars) and they
  break the single-central-mass assumption every formula here uses. Recording it as the
  first thing a 0.6 would revisit, not something to half-support now.
* **N-body anything.** The generator is a static architecture plus Kepler phases; orbits do
  not interact, do not precess, and do not evolve with the star's luminosity (a brightening
  Sun will not cook its Earth here).

## 14. Open questions

1. **~~Does the picker feel right at 300k stars?~~ Answered in 0.5.0.** §11.2's
   measurement: the frozen sky is inside budget, the dispatched walk is not. The
   pre-reject, not the residency-cell idea, is the build: a click is one point, so the
   cheap filter is the view axis.
2. **~~How many set members can the label layer ring before it is noise?~~ Answered in
   0.5.0:** `SET_RINGS_MAX = 16` (nearest-first, so the 16 drawn are the 16 nearest) plus
   the primary at full strength. If 16 still reads as noise the constant moves, nothing
   else changes.
3. **Is `budget` one slider or per-ship?** §7.4 makes it global; a per-leg override is
   obvious to want and obvious to over-build. Ship it global, revisit if the route report
   makes the global number awkward.
4. **Should the schematic be 2.5D?** §6 draws a flat plane with `cos i` squash. A tilted
   view (rotate the whole system by the camera's elevation) would look better and costs one
   transform per body — decide during 0.5.3-2, before the picking math assumes flat.
5. **WD and giant-star systems are the least constrained by data.** §4.4's weights for
   those rows are authored from the qualitative picture (remnant disks, engulfment). If a
   later measurement contradicts them, only the weight row changes.
6. **Does `system time` belong in the preset line?** It is view state like wave damping,
   which *is* in the preset — so yes by symmetry. Confirm it does not make pasted presets
   from before 0.5 behave oddly (absent key → default 0, which is the frozen case).
