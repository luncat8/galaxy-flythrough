## 2. 0.1.1 Camera Modes — Design

### 2.1 Modes

Three modes, cycled by `KeyC`:

1. **FLY** (current): 6-DOF momentum fly, WASD + mouse look, no target.
2. **ORBIT_GC**: orbit around Galactic Center (8.178, 0, 0 kpc). Camera always looks
   at target. Mouse drag = yaw/pitch around target. Wheel = distance to target
   (not speed). WASD = orbit strafe? For simplicity: in orbit mode, W/S = dolly
   in/out, A/D = orbit yaw, Q/E = orbit pitch. Shift/Ctrl still affect orbit angular speed.
3. **ORBIT_OBJECT**: orbit around selected object (star / solar system). Same controls
   as ORBIT_GC but target is dynamic. If no object selected, fall back to ORBIT_GC
   and show overlay hint "no selection — orbiting GC".

State machine in `camera.js`:

```js
const MODE_FLY = 0;
const MODE_ORBIT_GC = 1;
const MODE_ORBIT_OBJ = 2;

let mode = MODE_FLY;
let orbitTarget = Float64Array[3] = GC (8.178,0,0)
let orbitDistance = 8.5 kpc (start distance Sun->GC)
let orbitYaw, orbitPitch (derived from current camera pos)
```

`toggleMode()`:
- FLY -> ORBIT_GC: set target = GC, compute distance = |pos - target|, compute yaw/pitch
  from vector target->camera, snap camera to that orbit.
- ORBIT_GC -> ORBIT_OBJECT: if selection exists, target = selection.pos, distance = max(0.001, |pos-target|)
  else stay ORBIT_GC but overlay says "no object".
- ORBIT_OBJECT -> FLY: keep current pos/yaw/pitch, zero velocity, continue fly.

### 2.2 Orbit math

Camera-relative rendering already subtracts cameraPos in shader, so orbit math is same
as fly for viewProj, but view matrix looks at target.

Orbit update:
- `orbitYaw += input.lookDx * sensitivity + keys.left/right * dt * orbitAngularSpeed`
- `orbitPitch += input.lookDy * sensitivity + keys.up/down * dt * orbitAngularSpeed`
- Clamp pitch to ±(PI/2 - 0.02) same as fly.
- Position = target + spherical(orbitDistance, yaw, pitch):
  x = target.x + distance * cos(yaw)*cos(pitch)
  y = target.y + sin(yaw)*cos(pitch)
  z = target.z + sin(pitch)
- forward = normalize(target - pos)
- right, up recomputed from forward x worldUp (0,0,1) same as fly.

Dolly: wheel or W/S changes distance:
- distance *= 2^(-wheelDelta * k) or discrete *2 /2 per notch.
- Draft says "wheel adj speed: mul or div by 2" — for FLY mode that is speed,
  for ORBIT mode that is distance. Use same gesture, different meaning per mode.
- Clamp distance: 0.0001 kpc (0.1 pc) to 100 kpc.

No momentum in orbit mode: direct control, no velocity integration. Prevents drift
away from target. Keep velocity array but zero it on mode enter.

### 2.3 Speed control — FLY mode

Current:
- BASE_SPEED_KPC_S = 0.010 kpc/s = 10 pc/s = 32.6 ly/s
- SPEED_MULT_MIN 0.05, MAX 60, exponential wheel with gain 0.0015
- Boost 8x Shift

Required:
- Default 8 ly/s = 8 * 0.3066 pc = 2.453 pc/s = 0.002453 kpc/s
- Wheel: mul/div by 2 per notch (discrete), not continuous exponential
- Shift 100x, Ctrl 0.1x (Ctrl already used? Currently not — add as slow)
- Keep existing min/max but retune: min 0.05x = 0.4 ly/s, max 60x = 480 ly/s,
  with 100x boost = 800 ly/s max, 0.1x slow = 0.04 ly/s min. Reasonable for galaxy.

Implementation:

```js
const LY_TO_KPC = 0.000306601; // 1 ly in kpc (1 pc = 3.26156 ly)
const BASE_SPEED_KPC_S = 8 * LY_TO_KPC; // 0.0024528 kpc/s

// Wheel discrete: accumulate notches
if (input.wheelDelta !==0) {
  // wheelDelta >0 = scroll down = slower? Keep convention: down = slower.
  // Each 100 units = one notch (typical wheel ~100). Round to int steps.
  const steps = Math.round(input.wheelDelta / 100); // +1 = slower, -1 = faster?
  if (steps !==0) speedMult *= Math.pow(0.5, steps); // up = faster (div by 2 per notch down)
  // Actually spec: wheel adj speed mul or div by 2. So one notch = x2.
  clamp speedMult to [0.02, 200] to allow 0.16 ly/s to 1600 ly/s without boost
}

boost = (keys.boost ? 100 : 1) * (keys.slow ? 0.1 : 1)
```

Check current input.js: keys.boost exists, need keys.slow for CtrlLeft/Right.
Add `slow` key.

Expose `speedKpcPerSec = BASE_SPEED_KPC_S * speedMult * boost`
Overlay should print in ly/s: `speedLyPerSec = speedKpcPerSec / LY_TO_KPC`

Also print mode.

### 2.4 'h' — solar system location

Current `R` resets to START_POSITION = [0,0,0.005] kpc (Sun +5 pc up). Draft says 'h' -
solar sys location. Two interpretations:
- 'h' = home = same as R, or
- 'h' = go to solar system but keep orientation? While R resets orientation too.

Implement both: `KeyH` sets position to [0,0,0.005], zeroes velocity, sets mode=FLY,
yaw=0 pitch=0. Same as reset but separate action so R can remain as "reset" alias.
Add `actions.home`.

Alternatively 'h' could mean "focus Sun" while staying in orbit mode: if in orbit,
set target = Sun (0,0,0). Decide: in FLY mode, 'h' teleports to Sun; in ORBIT mode,
'h' sets orbit target to Sun and distance to 0.01 kpc (10 pc).

Spec: implement `goHome()` that:
- if mode==FLY: position = Sun, velocity=0, yaw=0 pitch=0
- if mode==ORBIT_*: target = Sun, distance = 0.01 kpc, recompute pos

### 2.5 Input mapping final

- E/Q: up/down in fly, pitch in orbit
- Mouse drag / pointer lock: look in fly, orbit yaw/pitch in orbit
- Wheel: speed x2 in fly, distance x2 in orbit
- ShiftLeft/Right: boost 100x (was 8x)
- CtrlLeft/Right: slow 0.1x (new)
- C: cycle camera mode
- H: home / solar system
- R: reset (keep as alias for home in fly)
- [ / ]: exposure (existing)
- P: future constellation toggle (0.1.2)
- O: future? Keep for object selection?

All deltas consumed in camera.step, zero alloc.

### 2.8 Edge cases

- Orbit distance 0: clamp to 0.0001 kpc to avoid singularity
- Pitch at ±90deg: same limit as fly, prevents gimbal lock
- Target = camera pos: push out by min distance
- Switching modes while dragging: consume lookDx/Dy before switch
- file:// pointer lock may fail — drag still works (existing logic)

### 3.3 Rendering

Two new render paths, but keep file:// friendly:

- Labels: canvas 2D overlay (not WebGPU text). Project landmark XYZ to screen via
  camera.viewProj, if in front and within ~0.5 kpc (?) draw name near projected pos.
  Use overlay div or 2D canvas on top of WebGPU canvas. Simpler: reuse #overlay? No,
  need separate #labels canvas or divs. Best: 2D canvas `labels` absolutely positioned,
  cleared each overlay tick (4 Hz) to avoid per-frame DOM.

- Constellation lines: WebGPU line pipeline or 2D canvas lines. Easiest for 0.1.2:
  2D canvas lines (same labels canvas) drawing line between projected star positions.
  No new WebGPU pipeline, keeps 0.1.1 independent. Later (0.1.5) move to WebGPU.

- Selection: ray cast on click. Find nearest landmark within screen threshold
  (e.g. 20 px). On click, set `selectedObject` in camera or in a new `Selection` module.
  Orbit mode uses selection as target.

## 4. 0.1.5 HDR Output with Range Adjustment

### 4.1 Current tonemapping

Star-sprite shader does:
```wgsl
flux = exp2(-MAG_TO_FLUX * magDiff)
brightness = flux / (1+flux) // Reinhard
```
This is already HDR-ish but exposure is single slider magZero.

### 4.2 Required

- HDR output: WebGPU canvas can be configured with `format: rgba16float` if supported,
  or keep `bgra8unorm` but do ACES tonemapping in shader.
- Range adjustment: UI for min/max exposure, or auto-exposure based on histogram?
  Simplest: two sliders [ ] for magZero, plus new keys for HDR range: maybe
  `;` `'` for HDR white point? Draft says "range adjustment".

Propose:
- Keep magZero as exposure (already [ ])
- Add HDR toggle 'h' conflicts — use 'o' for HDR? But 'h' is home. Use 't' for tonemap?
- Better: exposure already covers range, HDR means render to float texture then tonemap.

Implementation steps:
- `device.js`: request `rgba16float` format if adapter supports, fallback to `bgra8unorm`
- `star-sprites.js`: create intermediate texture if HDR, render stars to it, then fullscreen quad with tonemap
- `shaders.js`: add `tonemap` shader with ACES or Reinhard + exposure uniform
- `main.js`: add HDR params: `hdrExposure`, `hdrWhite`, controllable via keys
- Overlay: show HDR status

### 4.3 File changes

- `src/render/shaders.js`: add `tonemap` shader module
- `src/render/star-sprites.js`: add HDR pipeline, intermediate texture, two-pass render
- `src/core/input.js`: add HDR actions
- `src/main.js`: wire HDR controls
- `experiments/hdr-test.js`: validate tonemap curve, no NaN, exposure range

### 4.4 Deferred

HDR is 0.1.5, after landmarks. Don't implement until 0.1.2 stable. This plan just notes
the design so 0.1.1 camera doesn't block it (e.g. keep uniform layout extensible).

## 9. Open Questions

- Should orbit mode keep momentum? No — direct for precision.
- Should WASD in orbit mode orbit or pan target? Orbit for now, pan later via middle mouse.
- Selection: click or hover? Click to avoid accidental.
- Constellation lines in 3D or screen space? Screen space 2D lines are cheap and correct for nearby stars; for far stars 3D great-circle lines would be more accurate but overkill for 0.1.2.
- HDR: auto-exposure or manual? Manual first (magZero), auto later.
