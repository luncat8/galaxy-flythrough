# 0.2 — HDR Controls & Local Star Density Parity

Two visual problems reported after running the 0.1.5 HDR build:

1. **HDR whites out too fast.** Dense star fields (bulge, arm ridges, Sirius-style
   bright stars) clip to pure white before you can perceive their colour. The
   ACES Narkowicz curve is applied with an implicit white point of 1.0, so any
   summed flux above ~1.2 hits the shoulder and saturates. Need (a) a proper
   white-point parameter on the tonemap so highlights hold hue longer, and
   (b) an in-page menu with sliders for the three HDR knobs — exposure
   (magZero), brightness (ACES gain), and white point — instead of making the
   user hunt for bracket/semicolon keys.

2. **Visible density discontinuity near the Sun.** The Gaia/Hipparcos subset
   ships 3,829 catalog stars inside ~2.5 kpc, all packed around the camera.
   The procedural field (300k stars) is sampled from the analytical density
   model across the whole 25 kpc disc, so around the Sun it delivers only
   ~120 stars in the 0.5 kpc near-sphere (~220 stars/kpc³) while the catalog
   delivers 2,678 in that same sphere (~5,100 stars/kpc³). The 23× jump is
   visible as a dense "snow globe" of real stars around the camera against a
   much sparser procedural field. It is physically accurate (the solar
   neighbourhood really has been surveyed to much deeper magnitude) but
   visually distracting.

Both are tuning issues, not architecture changes. This plan captures the fix.

## 1. HDR menu slider

### New state

The renderer exposes three numbers instead of two:

| Knob | Old name | Range | Default | Meaning |
|---|---|---|---|---|
| Exposure | `magZero` | 0 – 22 | 17.0 | Faintest apparent magnitude that maps to flux 1.0 (`[` / `]`). |
| Brightness | `linearExposure` | 0.125 – 8.0 | 1.0 | Linear multiplier before the tone curve (`;` / `'`). |
| White point | **new** `whitePoint` | 1.0 – 16.0 | 6.0 | Scene-linear luminance mapped to display white by ACES. Higher = more highlight headroom, less clipping. |

Default `whitePoint = 6.0` is what Krzysztof Narkowicz's original ACES fitted
curve uses (the code in the wild always hard-codes it to 1.0 which clips fast);
at 6.0 a single bright star still reads as saturated colour rather than a white
blob, and dense bulges roll off through yellow/orange instead of jumping to
white.

### Curve change

```
aces(x) = clamp( (x/W)·(2.51·(x/W)+0.03) / ((x/W)·(2.43·(x/W)+0.59)+0.14), 0, 1)
```

i.e. divide input by W before ACES, then the standard curve. This is exactly
the "input scale" parameter Stephen Hill recommended in the original
Narkowicz comments and it maps scene luminance W to ~display white. The WGSL
tonemap uniform grows from `vec4f(exposure, pad, pad, pad)` to
`vec4f(exposure, whitePoint, pad, pad)`; the HDR-direct sprite path gains the
same extra float so the `;`/`'`/menu brightness multiplies linear output but
the white point is only meaningful on the SDR path (on a real HDR display the
display does the rolloff).

### UI

A settings panel `#menu` fixed in the top-right, toggled with **Tab** (and an
escape-to-close mirror). Three `<input type=range">` sliders with live value
labels, two reset buttons ("defaults" / "reset all"). Keyboard shortcuts
still work and update the sliders; dragging a slider updates the renderer.
No framework, no build — just DOM elements in `index.html` + a couple of
event listeners in `main.js`.

Styling matches the overlay aesthetic: monospace, dark translucent
background, green accent. The menu is small (~240 px wide) and starts
hidden so it does not interfere with screenshots or first impressions.

## 2. Star budget parity near the camera

### Diagnosis (empirical, from the actual bundle)

```
Catalog:  3,829 total stars (2,678 near band r<0.5 kpc, 1,151 medium 0.5-2.5 kpc)
Near-band volume: 0.524 kpc³
  → catalog density near Sun: 5,115 stars/kpc³

Procedural at 300k total, measured via sampleGalaxyStars:
  near (r<0.5 kpc):         114 stars → 218 stars/kpc³
  medium shell (0.5-2.5): 5,884 stars →  91 stars/kpc³
```

Ratio 23× near, 57× in the medium shell. The density model is correct
(0.065 stars/kpc³ scaled to 300k gives ~220/kpc³, which matches the
measurement). The catalog is *magnitude*-dense, not *volume*-dense: Gaia
sees every star brighter than G~12 out to ~0.5 kpc but drops off sharply at
fainter magnitudes. The visual discontinuity is therefore an artifact of the
magnitude limit, not a real density feature.

### Fix: density-aware budget allocation

The cell manager already has the concept of a `budgetStars` ceiling and a
stable residency set. We extend it to compute, per update, the expected
stellar density in each streaming cell from the analytical density field at
the cell centre, scaled by a **local** density normalisation that is the
key to avoiding the snow-globe:

```
// Normalise so total expected stars across all resident cells == VISUAL_STREAM_BUDGET (~3500)
rawMass   = Σ_c rhoTotal(cellCentre_c) * V_cell_c
localScale = VISUAL_STREAM_BUDGET / rawMass
expectedStars(cell) = rhoTotal(cellCentre) * V_cell * localScale
```

A galaxy-wide normalisation (`totalBudget / deliveredTotalMass`) would leave
the streaming volume starved: at 300k procedural + 250k catalog the density
at the Sun is only ~200 stars/kpc³ and a 0.5 kpc sphere gets ~120 stars —
the catalog's 2,678 would thin to a handful. By normalising *inside the
streaming volume itself* we get a rich-looking near field that matches what
the eye expects, and the density gradient still follows the analytical
model (more stars toward the disc midplane, toward the galactic centre,
along spiral arms) rather than appearing artificially uniform.

For each resident cell we then enforce parity:

1. Count `nCatalog` (already loaded for the cell), and compute
   `expected = expectedStars(cell)`. Landmarks live in their own buffer
   block and are never thinned.
2. If `nCatalog > expected`, thin catalog stars stably by deterministic
   FNV-1a hash (keep the highest-scoring `expected` stars, drop the rest
   from the upload entirely — invisible records are not copied, saving
   GPU bandwidth). Catalogged stars with `FLAG_LANDMARK` always score 2.0
   and are always kept regardless of budget.
3. If `nCatalog < expected`, generate `expected - nCatalog` extra **local
   procedural** stars into a per-cell gap-fill region of the star buffer
   so the cell reaches its expected count. These are generated with the
   same star-types pipeline used for the global field (uniform jitter
   inside the cell AABB, density-weighted component selection, IMF mass
   → Teff → colour/magnitude), keyed by `(localSeed, cellId, slot)` so
   they are stable across camera motion.

The result: every streaming cell delivers ≈`expectedStars(cell)` visible
stars. The near-Earth region no longer looks over-dense because the
catalog is thinned to the local expected density; cells under-served by
the catalog (most cells at medium/far bands) get local procedural fill
rather than appearing empty.

### Global budget accounting

The existing `proceduralTarget` counts only the *global* procedural field.
Gap-fill stars come from a separate `localProceduralBudget` sized to the
largest plausible shortfall (~20k stars, ~320 KB at 16 B/star). Default
total budget:

```
procedural (global)  300,000
landmarks                 ~60
catalog budget        250,000   (existing constant, now a thinning cap not a load cap)
local procedural       20,000   (gap fill, new)
```

The renderer's buffer layout grows to:

```
[0 .. globalProcedural)                         global procedural, generated once
[globalProcedural .. +landmarkCount)            named landmarks, written once
[+landmarkCount .. +localProceduralCapacity)    local gap-fill, rewritten per rebuild
[+localBase .. +localBase+catalogCapacity)      catalog, rewritten per rebuild
```

The local gap-fill region is re-filled on every cell-manager rebuild (same
0.25 s cadence), using the same stable hash so stars do not pop.

### Thinning stability

Hash-based thinning for catalog stars must be deterministic: the same star
in the same cell at the same budget is always kept or dropped. Using the
star's slot index × cell index × a fixed seed as the hash seed gives the
required stability, exactly matching §6 of the plan. We do NOT re-thin on
every frame — only when the residency set changes or the global budget
changes — so frame cost is zero during normal flight.

## 3. Implementation order

1. Add `whitePoint` to the tonemap uniform and the tonemap shader; update
   both SDR and HDR-direct paths (HDR-direct ignores it but still binds the
   uniform so layouts stay symmetric). Add `setWhitePoint()` to the
   renderer, expose on `state`. Update `star-sprites.js` defaults.
2. Add `#menu` DOM to `index.html`, style in `style.css`, wire up sliders
   in `main.js`. Toggle on Tab, update sliders on keyboard input, update
   renderer on slider input. Add Tab key to `input.js` as a one-shot
   `actions.menu`.
3. Compute expected counts in the cell manager, thin catalog records in
   place when they exceed the budget, keep landmarks. Extend the
   `writeInto` contract to return the thinned count and expose it via
   `stats()`.
4. Add local procedural gap-fill generation in `star-sprites.js`: for each
   cell in the residency set, sample `expected - catalogKept - landmarks`
   stars using the existing `SamplingLib`/`StarTypesLib` but with positions
   jittered inside the cell bounds (rather than drawn from the full-galaxy
   distribution). Key on `(localSeed, cellId, slot)` for stability.
5. Rebuild the staging buffer layout, bind groups and upload path to
   accommodate the new local-procedural region.
6. Update the overlay text to show `drawn = global + landmarks + local + catalog(thinned)`, and
   mention the menu key in the help text.

## 4. Out of scope

- Full magnitude-band completeness tracking (§7 of plan.md) still belongs
  to Milestone 4; the cell-local density parity here is a uniform thinning
  across magnitudes, which is a simpler approximation that is good enough
  to kill the visible blob and leaves the magnitude-aware version for
  later.
- The settings panel does not get a star-count slider yet; changing the
  global budget would require re-allocating the star buffer and
  re-generating the global field, which is a larger refactor. Left for a
  follow-up.
